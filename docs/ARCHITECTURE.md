# 아키텍처

코드가 지금 어떻게 생겼고 왜 그런지를 적는다. 기획은 [OVERVIEW.md](OVERVIEW.md), 설계 철학·결정 기록은 [PRINCIPLES.md](PRINCIPLES.md), 운영 명령은 [OPERATIONS.md](OPERATIONS.md), 개발 방법은 [DEVELOPMENT.md](DEVELOPMENT.md). 이 문서와 코드가 다르면 코드가 맞고, 이 문서를 고친다.

## 한눈에

```
브라우저 ──▶ gunicorn(duty-web) ──▶ Django 앱 duty ──▶ SQLite (data/db.sqlite3)
                                                         ▲
작업자 run_worker(duty-worker) ── 1분마다: 백업 → 상태 점검 → 알림 발송(텔레그램·웹 푸시)
캘린더 앱 ──▶ /calendar/<토큰>.ics (로그인 없이, 토큰으로)
```

- 앱 프로세스는 웹과 작업자 두 개뿐이다. 둘 다 같은 코드, 같은 `.env`, 같은 `data/`를 쓴다. 웹 앞에는 nginx 가 있다(설정 `deploy/duty-nginx.conf`, 느린 연결을 대신 받아 준다).
- 외부 연동 API는 없다. 바깥으로 나가는 것은 텔레그램 Bot API와 웹 푸시뿐이다.
- Tailscale Funnel로 공개된다(인터넷 → Funnel → nginx 127.0.0.1:8008 → gunicorn 127.0.0.1:8090). 모든 권한은 서버에서 검사한다(화면에서 버튼을 숨기는 것은 편의일 뿐).

| `duty/models.py` | 표 전부 | O |

| `duty/generator.py` | 장중관제 생성 알고리즘 | 없음 |
| `duty/csv_io.py` | 출근표 CSV 읽기·쓰기 | 없음 |
| `duty/ics.py` | 캘린더(ICS) 글자 만들기 | 없음 |

| `deploy/` | systemd 유닛 두 개 | |

순수 모듈(ORM 없음)은 입력을 받아 값을 돌려주기만 해서 DB 없이 테스트한다. 시각이 필요한 함수는 `now`/`today`를 인자로 받는다. 서비스에서 "오늘"은 반드시 `perms.today()`(테스트에서 바꿔 끼움).

## 데이터

```
Board(근무표) ─< BoardShift(근무 정의: 키·이름·시각·자격)
      ─< Department ─< User(멤버 겸 로그인 계정)
      ─< Period ─< Commute(날짜·멤버·출근조)         Period ─< PeriodEvent(상태 기록)
                ─< DutyAssignment(날짜·칸·멤버)      Period ─< ChangeLog(근무 변경 기록)
auth.Group: Board.admin_group(근무표 관리), Department.input_group(출근표 입력) ─< GroupKeeper(그룹 관리자)
User ─ RosterPref · CalendarFeed · TelegramAlarmProfile · PushAlarmSubscription · AlarmRule(─ Board) ─< AlarmDelivery
AlarmSettings(한 행: 봇 토큰, 장애 알림 chat_id, 푸시 키)
```

- **Board**(근무표): 지금은 IT 당번표(`code="it"`, 마이그레이션이 만든다) 하나. 부서·회차·근무 정의·보고서 알림 규칙이 근무표에 속하고, 사람은 부서를 통해 근무표 하나에 속한다(부서 없는 계정은 근무표 없음, `boards.board_of(user)`). 근무표를 만들면 관리 그룹 "<이름> 근무표 관리"가, 부서별 취합(`input_mode=collect`) 근무표에 부서를 만들면 입력 그룹 "<부서> 출근표 입력"이 저절로 생긴다. 회차 겹침·배포·배포 취소·그날의 주인·알림 계산은 근무표 안에서만 따진다. 서비스 함수는 근무표를 명시 인자로 받는다.

- **User**: `username` = 멤버 코드. `department`가 없으면 근무표에 안 나오는 관리 전용 계정. `is_active`(재직)를 끄면 근무표 후보에서 빠지고 로그인도 막힌다. 지난 근무·기록·통계에는 남는다. 근무표 후보는 `User.objects.roster()`.
- 이름(`User.name`)은 전체에서 고유하다. `>` `,` 줄바꿈 금지, `+`로 시작 금지(변경 체인·CSV 문법 문자).
- 서비스는 트랜잭션에 들어가자마자 회차를 다시 읽어(`refresh_from_db`) 화면이 읽은 오래된 상태로 결정하지 않는다.
- 정해진 값만 받는 칸은 `choices` + DB `CheckConstraint`(SQLite엔 enum이 없다). 기록을 남겨야 하는 FK는 `PROTECT`라서 근무·기록이 있는 사용자·회차는 지울 수 없다(비활성화한다).
- SQLite는 WAL, 트랜잭션은 `IMMEDIATE`(쓰기가 서로 줄 선다). 웹은 gunicorn 워커 1개·스레드 4개.

## 근무표와 칸

칸(cell) 키는 코드에 고정된 목록 `shifts.KEYS`(dawn, normal, dinner, slot0~slot9, night)이고 화면·기록·알림이 똑같이 쓴다. 이 순서가 알림·캘린더·`published_days`의 순회 순서다(바꾸면 알림 내용 hash가 달라져 최근 알림이 다시 나간다).

- **키 글자가 성격을 정한다**: `dawn`·`normal`·`dinner`·`night` = 근무조(`SHIFT_KEYS`, 한 사람 하루 하나, DB 제약), `slot0`~`slot9` = 장중관제(`SLOT_KEYS`, 자동 생성, 칸당 1명, 묶음 키 `slots`·이름 "장중관제"·짧은 이름 "관제").
- 근무표는 쓸 키를 골라 이름·시각·자격을 붙인다(`BoardShift`, 근무 정의). IT 정의는 마이그레이션이 그전 값을 그대로 넣었다: 새벽 06:30~15:30, 정상 08:00~17:00, 석식교대 09:00~18:00, 야간 13:30~21:30, 장중관제 10칸(08:30~18:00, 자격 출근조는 08:30 칸 = 정상, 17:00 칸 = 석식교대, 나머지 = 정상·석식교대, 자격 구분 = 개발자), 기본 알림 대상 = 새벽·석식교대·야간. 끈 정의(`active`)는 새 입력(입력 표·CSV 열, 부서 출근조·스케줄·알림 규칙 선택지, 생성)에서 빠지고(`boards.active_defs(board)`), 표시·지난 행·기록의 이름 찾기에는 남는다(`boards.defs(board)`는 꺼진 것까지 KEYS 순으로 돌려준다).
- `shifts.py`의 헬퍼(`cell_label`·`cell_start`·`cell_end`·`cells_of`·`display_order`·`shift_defs`·`slot_defs`)는 정의 목록을 첫 인자로 받는 순수 함수다. 기본값이 없다. 알림 문구(`alarms/messages`)·일정(`schedule`·`plan`)도 같다.
- 화면 순서: 근무조(시작 시각 순) → 장중관제(키 순).
- 장중관제 배정은 `DutyAssignment(cell="slotN")` 행으로 저장한다(읽을 때 계산하지 않는다). 관제 칸당 한 명은 조건부 unique 제약이 보장한다. 배포 때 지운 행은 `publish_undo`에 `["c", 회차, 날짜, 멤버, 출근조]`(출근표)·`["a", 회차, 날짜, 멤버, "slotN"]`(배정)로 보관한다.
- 근무표와 근무 정의는 관리 화면 "근무표"에서 보기만 한다(1단계). 근무표 추가·편집·근무 정의 편집은 3단계에서 설계 4.3 검증과 함께 연다. code 는 `boards.it_board()` 가 IT 근무표를 찾는 열쇠라 바꾸지 않는다.
- 대상 날짜는 회차 기간의 월~금(휴장일 처리 없음).

## 역할

권한은 `auth.Group` 멤버십으로만 판단한다(`perms.py`: `admin_boards`·`is_board_admin`·`is_admin`·`managed_departments`·`can_edit`·`assert_can_edit`). Django permissions와 "스태프 권한"(`is_staff`)·슈퍼유저는 근무표 권한에 쓰지 않는다(`is_staff`는 관리 화면 출입 조건 `admin.site.has_permission`에만 남는다).

| 누가 | 무엇 |
|---|---|
| 멤버(로그인한 누구나) | 근무표·내 근무 조회, 내 근무표의 오늘·미래 근무 변경, 내 알림·캘린더 |
| 출근표 입력 담당(부서 입력 그룹 멤버, `Department.input_group`) | 취합 중인 회차에 자기 부서 출근표 입력 |
| 근무표 관리자(근무표 관리 그룹 멤버, IT = "IT 근무표 관리") | 그 근무표의 회차 관리·생성·배포, 통계, 변경 이력, 지난 날짜 수정, 그 근무표 전 부서 출근표. 회차 뷰는 `_period(request, pid)`가 검사(아니면 404). 메뉴 [회차]·[이력]은 어느 근무표든 관리자면 보인다. [통계]는 slot* 정의가 있는 근무표의 관리자에게만 보인다(`perms.stats_boards`). 통계 화면은 그중 id가 가장 작은 근무표를 보여 주고, 없으면 403이다(근무표 고르기는 2단계) |
| 그룹 관리자(`GroupKeeper`) | 그 그룹에 멤버를 넣고 빼는 사람으로 기록만 해 둔다(지정·멤버를 고치는 화면은 3단계. 그때까지 멤버는 슈퍼유저가 관리 화면 "사용자"의 "그룹" 칸에서 넣는다) |
| 슈퍼유저 | Django 관리 화면: 사용자("그룹" 칸으로 근무표 관리자 지정)·부서·근무표와 근무 정의(1단계는 보기만)·그룹(이름, 그룹 관리자는 보기만)·계정 발급·로그인 잠금 해제·알림 설정. 근무표 관리자 권한은 자동으로 받지 않는다(관리 그룹에 넣어야 한다) |

- 그룹 관리자는 `Group`에 걸린 표라서(근무표로 가는 FK가 없다) 관리 화면 "그룹"에 보기 전용 인라인으로 보인다(편집은 3단계). 근무표 화면에서는 관리 그룹이 읽기 전용으로만 보인다.
- 저장된 부서의 근무표는 바꿀 수 없다(`admin.DepartmentForm` 의 board 칸이 읽기 전용, 새 부서만 고른다. 옮기기는 필요해지면 별도 기능). 부서 순서(`Department.order`, 기본 99 = 맨 뒤)가 근무표 화면 부서 필터의 순서다.
- 사람의 부서를 바꿔 근무표가 달라지면 `accounts.on_department_change(user, old_department_id)`가 개인 알림 발송 기록을 정리한다. 지금 이 함수를 부르는 곳은 관리 화면 사용자 저장(`UserAdmin.save_model`) 하나뿐이다. 부서를 바꾸는 다른 길을 만들면 그 길에서도 반드시 불러야 한다.

## 회차

```
작성 중 ⇄ 취합 중 ⇄ 마감  ──생성──▶ 생성됨 ──배포──▶ 배포됨
   ▲________________________________│  (상태 바꾸기)    │
                                     ◀────배포 취소─────┘ (가장 최근 배포만)
```

- 회차는 근무표 하나에 속한다(관리하는 근무표가 여럿이면 만들 때 고른다). 작업 중·취합 중·마감끼리는 `periods.move`로 자유롭게 오간다. 생성됨에서 나가면 장중관제만 지우고 출근표는 남는다. 기간은 작성 중에서만 고친다(줄이면 기간 밖 행을 지운다). 새로 만들거나 기간을 고칠 때 같은 근무표의 다른 배포 전 회차와 겹치면 막는다(배포 취소로 돌아온 회차는 겹칠 수 있고, 배포할 때 덮어쓰기로 정리된다).
- 배포되지 않은 회차는 [회차 삭제]로 지울 수 있다(출근표·생성 결과·상태 기록까지). 근무 변경 기록이 남은 회차(배포된 적 있음)는 기록 보존을 위해 지울 수 없다.
- 생성됨은 [생성]으로만, 배포됨은 [배포]로만 들어간다. 상태가 바뀔 때마다 `PeriodEvent`(언제·누가·무엇에서 무엇으로·메모)를 남긴다.
- **출근표 입력**(`services/collect.py`): 회차와 같은 근무표의 부서만 받는다. 표에서 직접 고치거나 CSV를 올린다. CSV는 UTF-8(BOM)→CP949 순으로 읽고, 하나라도 틀리면 아무것도 반영하지 않고 (위치, 사유)를 보여 준다. 올리면 그 부서의 회차 출근표 전체를 파일 내용으로 바꾼다. 저장할 때 꺼진 근무조 정의의 행만 그대로 두고, 부서 출근조에서 뺀 근무조의 행은 지운다(`collect._kept_keys`).
- **생성**(`generator.py`, `services/generate.py`): 그 근무표 부서마다 평일이 다 차야 한다(IT = 4개 부서). 칸 목록은 그 근무표의 관제 정의(`slot_defs`, 키 순)이고, 관제 정의가 없는 근무표는 생성할 것이 없다.
  1. 날짜마다 자격자가 적은 칸부터, 그날 아직 안 받은 자격자 중 지금까지 배정이 가장 적은 사람(같으면 무작위). 한 사람 하루 한 칸.
  2. 최다·최소 차이(편차)가 2 이하가 될 때까지 많이 받은 사람의 칸을 적게 받은 자격자에게 넘긴다.
  - 후보는 그 근무표 부서의 재직자 중 관제 정의의 자격 구분(IT = 개발자)에 드는 사람이고, 횟수는 기간 중 한 번이라도 자격이 있던 사람끼리만 비교한다(통계도 같다). 회차 화면의 배정 횟수 표도 같은 모집단이다(`stats.period_duty_counts`: 그 근무표 부서의 재직자. 배정 0회인 퇴사자는 줄이 없고, 배정받은 퇴사자는 배정 수로 남는다). 못 채우는 칸이 있으면 아무것도 쓰지 않고 날짜·칸을 보여 준다. 무작위 씨앗은 `Period.seed`에 남는다.
- **배포**(`services/publish.py`): 덮어쓰기 시작일 `S`를 고른다. 같은 근무표의 다른 배포 회차의 `[S, 이 회차 종료일]` 행과 이 회차의 `S` 이전 행을 지운다. 지운 행은 `Period.publish_undo`(JSON)에 보관한다. ChangeLog는 지우지 않는다.
- **그날의 주인**(`boards.owner(board, d)`, 여러 날은 `owners`): 그 근무표의 배포 회차 중 `overwrite_from ≤ d ≤ end_date`인 것 가운데 가장 최근에 배포한 것(배포 `PeriodEvent` 순번. 배포 이벤트가 없는 옛 회차는 그보다 오래된 것으로 보고 `published_at`·pk 순). 배포 때 지우는 규칙과 같은 결과라 행이 없는 날에도 주인이 있다. 근무 변경(`changes._owner`), 조회(`services/roster.py`의 `published_days`: 주인이 있는 평일마다 그 회차의 행. 행이 없으면 빈 칸이고 정기 알림·캘린더에는 넘기지 않는다), 변경 알림의 `_live`, 배포 미리보기가 모두 이 함수를 쓴다. 화면 칸의 변경 기록도 주인 회차 것만 보이므로 덮어쓰인 회차의 ChangeLog는 숨겨진다.
- **배포 취소**: 그 근무표에서 가장 최근에 배포한 회차만. 보관한 행을 되살리고 회차는 생성됨으로 간다. 중간 회차는 뒤 배포부터 차례로 취소한다. 배포 뒤 수정은 회차 데이터에 남지만, 배포 취소 때 그 시점의 ChangeLog 최대 번호를 `Period.log_floor`에 적고, 그 이하 기록은 다시 배포해도 화면·알림에 쓰지 않는다(기록은 남는다). 순서는 근무표마다 `PeriodEvent` 순번으로 정한다. 이 기능 전에 배포한 회차(`publish_undo` null)는 취소할 수 없다.

## 근무 변경

`services/changes.py` 한 곳에서 한다.

- 서비스 공개 함수(`change_cell`·`exchange`·`swap`, 첫 인자 다음에 근무표) 첫 줄에 `perms.assert_can_edit(user, board, d)`: 그 근무표 부서 사람이거나 그 근무표 관리자만 바꾼다. 오늘 이전 날짜는 그 근무표 관리자만. 출근표 입력의 지난 날짜 판단도 `perms.is_board_admin(user, period.board)`.
- 근무 변경 창(`changes.exchange`)의 기본은 **맞교환**: From(이 칸 사람)과 To 를 고르면, To 가 그날 같은 종류(출근조끼리·관제끼리) 다른 칸에 있으면 서로 바꾸고(`swap`), 없으면 From 대신 들어간다(`change_cell`). 출근조 칸의 넣기만·빼기만은 목록 끝 "(없음)"을 고르고 확인창을 거친다. 관제 칸은 바꾸기만. 새로 들이는 사람은 그 근무표 부서의 재직자만.
- 관제 자격이 안 맞거나 같은 날 다른 관제 칸도 맡으면 막지 않고 경고만 한다(대신 서기).
- 모든 변경은 ChangeLog(`before`/`after`)에 남는다. 화면은 이를 이어 붙여 교체 `A>B`, 추가 `+B`, 제거(취소선)로 그린다. 동시 수정은 먼저 저장한 쪽이 이긴다.

## 알림

- **내 근무가 바뀌면 알림**(`User.notify_changes`, 기본 켬): 작업자가 매분 `change_notice.tick`으로 아직 안 보낸 ChangeLog(`notified=False`)를 보고 당사자(From·To, 바꾼 본인 제외)에게 연결된 텔레그램·푸시로 보낸 뒤 `notified`로 표시한다. 오늘 이전 날짜·하루 넘게 밀린 기록은 보내지 않는다. 실패는 다시 보내지 않는다(로그만).
- 사용자가 규칙(`AlarmRule`)을 만든다. 종류는 **개인**(내 근무) / **보고서형**(부서·유형·스케줄로 거른 그날 출근표). 시점은 근무 시작 N분 전 / N일 전 몇 시 / N영업일 전 몇 시. 채널은 텔레그램·웹 푸시. 보고서 규칙은 근무표 하나에 속한다(근무표 선택 칸은 근무표가 둘 이상일 때만 보이고, 하나뿐이면 그 근무표). 개인 규칙은 내 부서의 근무표를 따른다. 기본 규칙(계정 첫 발급)은 근무 정의의 "기본 알림 대상" 근무조로 만든다.
- 작업자가 매분 `alarm_runner.tick`: 근무표마다 그 근무표의 `published_days`(배정 있는 날만)와 그 근무표 규칙(개인 = 주인 부서의 근무표, 보고서 = `rule.board`)만 넘겨 그 근무표 정의로 `alarms.plan`을 따로 부른다(같은 날 다른 근무표 때문에 취소 알림이 나가지 않게). 지금 보낼 것을 `senders`로 보낸 뒤 `AlarmDelivery`를 남긴다(목적지별, **보낸 뒤에** 기록). 같은 내용은 `last_sent_hash`로 다시 보내지 않고, 근무가 바뀌면 변경·취소 알림을 보낸다. 규칙의 근무표(`board_id`)도 `RULE_FIELDS`에 있다. 관리 화면에서 사람의 부서를 바꿔 근무표가 달라지면 그 사람 개인 규칙의 오늘 이후 `AlarmDelivery`를 지운다(`accounts.on_department_change`).
- 발송 실패는 `Gone`(구독 삭제) / `Permanent` / `Temporary`·`RetryLater`(백오프 후 재시도)로 나눈다.
- 봇 토큰·푸시 키는 DB `AlarmSettings`(슈퍼유저가 관리 화면에서). 푸시 키는 비어 있으면 자동으로 만든다. 봇을 바꾸면 모든 텔레그램 연결 확인을 비운다.
- 텔레그램 연결: 사용자가 일회용 코드를 봇에 보내면 [연결 확인]이 `getUpdates`로 찾는다(파일 잠금으로 한 번에 하나).

## 화면 디자인

- Pico.css + `base.html`의 공통 스타일. NEXTRADE BI를 따른다: 로고·심볼은 `duty/static/duty/`의 원본 그대로(비율·색 변경 금지), 어두운 배경(다크 모드)은 흰색 단색(CSS `filter`). 지정 서체 Noto Sans KR(없으면 시스템 글꼴, 글꼴 파일은 싣지 않는다).
- 화면 모드: 상단 버튼으로 시스템·라이트·다크(기기마다 localStorage, `<html data-theme>`). 다크용 색은 `base.html` 맨 위 변수 두 곳(시스템 다크·직접 다크)에만 두고, 화면 규칙은 변수(`--chg`·`--logo-filter` 등)만 쓴다.
- 색: PURPLE `#2B1B40` = 주요 동작 버튼·현재 위치, RED `#E50038`(`--nxt-red`) = 로고·오류·위험 동작, 그리고 "오늘" 표시(달력처럼 읽힌다)만. 일반 버튼에 빨강을 쓰지 않는다(빨강 = 위험으로 읽힌다).
- 화면마다 다음 단계 하나만 채운 버튼, 되돌리기·다시 하기는 테두리 버튼, 지우기는 맨 아래 "위험 구역"(빨간 테두리) + 확인창.
- 메시지는 `messages` 종류대로 색과 기호(✓ 성공, ! 오류, ⚠ 경고)로 구분한다. 입력칸은 placeholder 말고 `<label>`(`form.labeled`).
- 모바일(390px): 메뉴는 줄바꿈(숨은 메뉴 없음), 주간 근무표는 하루씩 세로로, 검색·필터는 접힘. 필터 체크박스로 다시 불러올 때는 스크롤 위치와 펼침 상태를 되살린다(`_filters.html`, sessionStorage).
- 근무표 보기 설정(`RosterPref`: 부서·유형·스케줄·주간/월간·변경 내역 표시)은 사람마다 저장된다. 변경 내역을 끄면 `A>B`·`+B`는 지금 사람만, 빠진 사람(취소선)은 숨긴다. 화면을 바꾸면 PC 1400px·모바일 390px·다크 모드를 직접 본다.

## DB를 바꾸려면 (SQLite → MySQL 등)

코드는 ORM만 쓰므로 모델·서비스·화면은 그대로다. SQLite에 묶인 곳은 두 군데다.
- `services/backup.py`(백업·복원·검사): SQLite 파일 전용. DB 쪽 덤프·자동 백업으로 바꾸고, `health.py`의 "최근 백업" 점검을 맞춘다.
- 동시 수정: 지금은 `transaction_mode=IMMEDIATE`로 쓰기가 줄을 서서 `transaction.atomic()` 안의 "읽고 확인 → 쓰기"가 안전하다. 다른 DB에서는 서비스의 atomic 블록마다 읽는 행을 `select_for_update()`로 잠가야 한다(근무 변경, 출근표 입력, 생성·배포·배포 취소, 알림 기록 등).
- 작업자 한 개 보장은 파일 잠금이라 서버가 한 대일 때만 맞다.

## 보안·개인정보

- 로그인 5회 실패 시 그 아이디가 15분 잠긴다(django-axes). 비밀번호 변경의 '지금 비밀번호' 확인도 같이 센다.
- `config/wsgi.py` 가 Django 앞에 `duty/guard.py` 를 둔다: 본문 2MB 초과 413, 15초 안에 본문이 다 오지 않으면 408, 로그인·비밀번호 변경 POST 는 동시에 2개까지(넘치면 429). nginx 가 느린 연결을 먼저 받아 주고, 가드는 nginx 없이 돌 때(개발 PC)나 nginx 설정이 빠졌을 때의 한 번 더 막는 장치다.
- 로그인한 화면은 `Cache-Control: private, no-store`(`duty/middleware.py`). 로그 파일은 하루 50MB 를 넘으면 그날은 버린다(`duty/logging.py`).
- 계정 초기화(재발급)는 캘린더 구독·텔레그램·푸시 연결도 끊는다. 텔레그램은 `/start <일회용 코드>` 로만 연결한다(chat_id 직접 입력 없음).
- 백업 사본에서는 로그인 세션을 지우고 파일 권한을 600 으로 둔다.
- 실명은 커밋하지 않는다. 테스트는 가상 이름만 쓴다.
- 로그·화면·메시지에 남기지 않는 것: 봇 토큰·푸시 개인키 원문(관리 화면은 끝 4자리만), 캘린더 토큰·피드 경로, 텔레그램 연결 코드, 푸시 endpoint, 메시지 본문.
