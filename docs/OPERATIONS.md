# 운영

사내 서버(RHEL 9.4+)에 설치하고 돌리는 방법. 명령은 그대로 복사해 쓰는 형태다(셸 함수·별칭 없음). 구조와 이유는 [ARCHITECTURE.md](ARCHITECTURE.md), 개발 환경은 [DEVELOPMENT.md](DEVELOPMENT.md).

## 폴더 구조

개발 PC 와 서버가 같은 모양이다(서버는 `/opt/duty_generator`).

| 위치 | 무엇 | git |
|---|---|---|
| `config/`, `duty/`, `manage.py` | 코드. `config/` 는 Django 프로젝트(설정을 읽는 `settings.py`, URL, WSGI), `duty/` 는 앱 본체(모델·화면·서비스·관리 명령·템플릿·정적 파일). 설치하지 않고 이 폴더에서 바로 돈다. | 올림 |
| `tests/` | pytest 테스트. | 올림 |
| `requirements.in` / `requirements.lock` / `requirements-dev.txt` | 직접 쓰는 라이브러리(범위) / 운영 설치용 고정 버전 / 개발용 테스트 도구. | 올림 |
| `pyproject.toml` | pytest 설정만. | 올림 |
| `deploy/` | 서버용 systemd 유닛 두 개 `duty-web.service`(웹)·`duty-worker.service`(작업자)와 nginx 설정 `duty-nginx.conf`. 아래 "서비스"·"nginx". | 올림 |
| `docs/ARCHITECTURE.md` | 구조와 도메인 규칙. 코드를 고치기 전에 읽는다. | 올림 |
| `.env.example` → `.env` | 설정값. 견본을 `.env` 로 복사해 채운다. 개발 PC 와 서버의 차이는 이 파일의 값뿐이다. | `.env` 는 안 올림 |
| `data/` | 실행 중 생기는 파일 전부: `db.sqlite3`(DB), `backups/`(백업), `logs/`(로그), 잠금 파일. `.env` 의 `DUTY_DATA_DIR` 로 옮길 수 있다. | 안 올림 |
| `.venv/`, `staticfiles/` | 파이썬 가상환경, 모은 정적 파일(`collectstatic`). 운영(DEBUG 꺼짐)은 이름에 해시를 붙인 파일과 `.gz`·해시 목록 `staticfiles.json` 을 만든다 — **업그레이드 때 `collectstatic` 을 빠뜨리면 화면이 500** 이다. | 안 올림 |

## 개발 PC 와 운영 서버의 차이

차이는 `.env` 값으로만 정한다. 항목마다 설명과 예시 값은 `.env.example` 에 있다.

| 설정 | 개발 PC | 운영 서버 |
|---|---|---|
| `DUTY_DEBUG` | `1`(오류 상세 화면, http 쿠키 허용) | `0` |
| `DUTY_SECRET_KEY` | 비움(개발용 키) | 무작위 값(필수) |
| `DUTY_ALLOWED_HOSTS` | 비움(`127.0.0.1,localhost`) | `duty.example.ts.net,127.0.0.1,localhost` |
| `DUTY_CSRF_ORIGINS` | 비움 | `https://duty.example.ts.net` |
| `DUTY_SITE_URL` | 비움 또는 `http://127.0.0.1:8000` | `https://duty.example.ts.net` |
| `DUTY_ADMIN_PATH` | 비움(`admin`) | 짐작하기 어려운 값(필수: 비우거나 `admin` 이면 서버가 뜨지 않는다) |
| `DUTY_DATA_DIR` | 비움(`data/`) | 비움(`/opt/duty_generator/data`) |
| `DUTY_REPO_URL` | 줄 없음(기본 `https://github.com/sanggae4133/duty_generator`) | 줄 없음(같음). `DUTY_REPO_URL=` 처럼 일부러 비우면 화면 아래 "Made by SJ · GitHub" 를 숨긴다 |
| `DUTY_BACKUP_HOUR` / `DUTY_BACKUP_KEEP_DAYS` / `DUTY_LOG_KEEP_DAYS` | 비움(3시 / 30일 / 14일) | 비움(같음) |
| `DUTY_BACKUP_COPY_DIR` | 비움(끔) | 비움 또는 다른 디스크·NAS 폴더(아래 "백업·복원") |

텔레그램 봇 토큰·웹 푸시 키·장애 알림 chat_id 는 `.env` 가 아니라 관리 화면 → 알림 설정(DB)에 둔다(아래 "알림").

실행하는 것도 같다. 개발 PC 는 손으로 켜고, 서버는 systemd 가 켠다.

| 무엇 | 개발 PC | 운영 서버 |
|---|---|---|
| 웹 | `.venv/bin/python manage.py runserver` | `duty-web.service`(gunicorn) |
| 작업자(알림·백업·상태 점검) | 필요할 때 `.venv/bin/python manage.py run_worker` | `duty-worker.service` |

## 설치 (사내 서버)

RHEL 9.4 이상 기준(Python 3.12 패키지는 9.4 부터, 시스템 SQLite 3.34 — Django 5.2 는 SQLite 3.31 이상이 필요해서 **RHEL 8 은 안 된다**). 코드는 root 소유(`duty` 는 읽기만), 쓰는 곳은 `data/` 하나(`duty` 소유)다.

```bash
sudo dnf install -y python3.12 python3.12-pip git curl     # 기본 python3(3.9)가 아니라 python3.12 를 쓴다
sudo useradd -r -s /sbin/nologin duty
sudo git clone https://github.com/sanggae4133/duty_generator.git /opt/duty_generator
cd /opt/duty_generator
sudo install -d -o duty -g duty -m 750 data data/backups data/logs
sudo python3.12 -m venv .venv
sudo .venv/bin/pip install -r requirements.lock
sudo install -o root -g duty -m 640 .env.example .env
sudoedit .env   # 견본은 개발 PC 값이다. 여섯 줄을 "서버:" 값으로: DUTY_DEBUG=0, DUTY_SECRET_KEY, DUTY_ALLOWED_HOSTS, DUTY_CSRF_ORIGINS, DUTY_SITE_URL, DUTY_ADMIN_PATH
sudo .venv/bin/python manage.py collectstatic --noinput   # root 로: 코드 폴더는 duty 가 쓸 수 없다
sudo -u duty .venv/bin/python manage.py migrate   # 개발 PC DB 를 가져가면 여기서 멈추고 아래 "개발 PC DB 를 서버로 옮기기"
sudo -u duty .venv/bin/python manage.py createsuperuser  # 첫 어드민: 아이디·이름·비밀번호를 묻는다. 이어서 아래 "처음 한 번: 계정 만들기"대로 근무표 관리 그룹에 넣는다
sudo -u duty .venv/bin/python manage.py check --deploy   # 경고 확인(HTTPS 는 Funnel 이 맡으므로 SSL_REDIRECT 경고는 무시)
sudo cp deploy/*.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now duty-web duty-worker
sudo dnf install -y nginx                                   # 웹 앞단(아래 "nginx")
sudo cp /etc/nginx/nginx.conf /etc/nginx/nginx.conf.orig    # 패키지 기본 설정을 남겨 둔다
sudo cp deploy/duty-nginx.conf /etc/nginx/nginx.conf        # 기본 설정을 통째로 바꾼다(80 포트 안내 페이지 없음)
sudo nginx -t                                                # syntax is ok / test is successful
sudo setsebool -P httpd_can_network_connect 1               # 1~3분 걸린다. getenforce 가 Disabled 면 건너뛴다
sudo systemctl enable --now nginx
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8008/login/   # 200
```

- SELinux(기본 enforcing)에서도 기본 정책으로 돈다(서비스는 `/opt` 의 가상환경을 실행하고 `data/` 에만 쓴다). 서비스가 `Permission denied` 로 안 뜨면 `sudo ausearch -m avc -ts recent` 로 거부 기록을 보고, 파일을 다른 곳에서 옮겨 왔다면 `sudo restorecon -R /opt/duty_generator` 로 라벨을 되돌린다.
- 웹(8090)과 nginx(8008)는 `127.0.0.1` 에만 열고 바깥 공개는 Tailscale Funnel 이 맡으므로 firewalld 는 열 것이 없다. nginx 는 패키지 기본 설정(80 포트 안내 페이지)을 쓰지 않고 `deploy/duty-nginx.conf` 로 통째로 바꾸므로 80 도 열지 않는다.
- `DUTY_SECRET_KEY` 는 `python3 -c "import secrets;print(secrets.token_urlsafe(48))"` 로 만든다.
- `.env` 를 고친 뒤에는 `sudo systemctl restart duty-web duty-worker`.
- 서버 명령은 모두 `cd /opt/duty_generator` 에서 실행한다. `manage.py` 는 항상 `sudo -u duty .venv/bin/python manage.py ...` 로 부른다(DB·로그 파일 주인이 `duty` 라서).
- 서버 시계: 알림이 분 단위로 돈다. `timedatectl` 에서 `System clock synchronized: yes`. 시간대와 상관없이 앱은 Asia/Seoul 로 계산한다.
- 작업자는 켜질 때 26시간 안에 만든 백업이 없으면(새 설치·오래 꺼져 있었음) 시각과 상관없이 바로 하나 만든다. 그래서 상태 점검이 "백업 없음"으로 시작하지 않는다.
- `sudo -u duty .venv/bin/python manage.py check --deploy` 가 `DEBUG`·`SECRET_KEY` 경고를 내면 `.env` 의 여섯 줄을 덜 바꾼 것이다.
- 알림은 관리 화면 → 알림 설정에 봇 토큰을 넣어야 나간다(아래 "알림 켜기").

## 서비스 (`deploy/`)

앱은 아래 두 유닛이고 `/etc/systemd/system/` 에 복사해서 쓴다. 앞단 nginx 는 RHEL 패키지의 `nginx.service` 를 그대로 쓰고 설정 파일만 넣는다. 각 줄의 뜻은 파일 안 주석에 있다.

| 유닛 | 하는 일 | 로그 |
|---|---|---|
| `duty-web.service` | 웹. `gunicorn config.wsgi:application --bind 127.0.0.1:8090 --workers 1 --threads 4` | `data/logs/web.log`, `journalctl -u duty-web` |
| `nginx.service`(RHEL 패키지) | 웹 앞단. 설정은 `deploy/duty-nginx.conf` → `/etc/nginx/nginx.conf`(아래 "nginx") | `/var/log/nginx/duty-error.log`, `journalctl -u nginx` |
| `duty-worker.service` | 작업자 `manage.py run_worker`. 1분마다: 알림 발송(매분), DB 백업(하루 한 번 `DUTY_BACKUP_HOUR` 시 이후), 상태 점검(5분마다) | `data/logs/worker.log`, `journalctl -u duty-worker` |

`duty-web.service` 의 줄:
- `User=duty` — `duty` 사용자로 돈다. 코드는 읽기만 하고 `data/` 에만 쓴다.
- `WorkingDirectory=/opt/duty_generator` — 여기서 돌아야 `config`·`duty` 를 찾는다(설치 없이 저장소에서 바로 돈다).
- `ExecStart=... --bind 127.0.0.1:8090` — 서버 안에서만 연다. 앞에 nginx(8008)가 있고 바깥 공개는 Tailscale Funnel 이 맡는다. 이 주소를 바꾸면 `deploy/duty-nginx.conf` 의 `proxy_pass` 도 바꾼다.
- `--workers 1 --threads 4` — 프로세스 하나에 스레드 4개. `web.log` 를 한 프로세스만 써야 자정에 파일을 넘길 때 꼬이지 않는다. 사용자가 수십 명이라 충분하다.
  느린 연결은 앞단 nginx 가 받아 주고, 앱 안의 요청 가드(`duty/guard.py`)는 2MB 넘는 요청 413, 15초 안에 본문이 다 오지 않는 요청 408, 동시에 몰린 로그인 POST 429 로 한 번 더 막는다.
- 접근 로그(`--access-logfile`)는 켜지 않는다 — 캘린더 구독 주소에 비밀 토큰이 들어 있다.
- `NoNewPrivileges`·`PrivateTmp`·`ProtectSystem=strict`·`ProtectHome`·`ReadWritePaths=/opt/duty_generator/data` — 샌드박스. 앱에 코드 실행 구멍이 생겨도 시스템·`/home` 은 읽기 전용이거나 보이지 않고 쓰기는 `data/` 하나만 된다. `.env` 의 `DUTY_DATA_DIR` 을 바꾸면 `ReadWritePaths` 도 같이 바꾼다.
- `Restart=always`, `RestartSec=5` — 죽으면 5초 뒤 다시 띄운다.
- `WantedBy=multi-user.target` — `enable` 해 두면 부팅 때 켜진다.

`duty-worker.service` 의 줄:
- `User`, `WorkingDirectory`, `Restart`, `WantedBy`, 샌드박스 다섯 줄 — 웹과 같다.
- `ExecStart=... manage.py run_worker` — 작업자. `data/.alarms.lock` 잠금으로 한 번에 하나만 돈다(같은 알림이 두 번 가지 않게). 한 작업이 실패해도 로그(`worker job failed: <작업>`)만 남기고 다른 작업은 계속한다.

유닛을 고쳤거나 새 버전에서 바뀌었으면 `sudo cp deploy/*.service /etc/systemd/system/ && sudo systemctl daemon-reload` 후 재시작한다.

## nginx (웹 앞단)

인터넷 → Tailscale Funnel(HTTPS) → **nginx `127.0.0.1:8008`** → gunicorn `127.0.0.1:8090`.

웹(gunicorn)은 스레드가 4개뿐이라, 요청 본문을 아주 느리게 보내는 연결 몇 개만 있어도 사이트 전체가 멈춘다. nginx 는 이런 연결 수천 개를 적은 메모리로 들고 있다가, 요청을 끝까지 다 받은 것만 gunicorn 에 넘긴다. 설정은 저장소의 `deploy/duty-nginx.conf` 하나이고, 서버에서는 패키지 기본 설정 `/etc/nginx/nginx.conf` 를 이 파일로 **통째로 바꿔서** 쓴다(기본 설정에 든 80 포트 안내 페이지를 없애려고. 패키지 업데이트는 이 파일을 덮어쓰지 않는다). 각 줄의 뜻은 파일 안 주석에 있다.

로그인·관리 화면 로그인·비밀번호 변경 POST 는 접속 IP 마다 1분에 10번(한 번에 10번까지는 바로)으로 묶는다(넘치면 429 "Too Many Requests"). 앱은 이 POST 를 사이트 전체에서 동시에 2개만 받으므로(`duty/guard.py`), 묶지 않으면 익명 한 명이 계속 보내 모든 사람의 로그인을 막을 수 있다. 사무실처럼 한 IP 를 여럿이 쓰는데 429 가 자주 보이면 `limit_req` 의 `burst` 를 올린다.

### 이미 운영 중인 서버에 처음 넣기 (한 번만, 20분)

- 이 문서는 **GitHub 웹에서 보면서** 한다(서버의 옛 문서에는 이 절이 없다).
- 사람이 적게 쓰는 시간(저녁)에 한다. 2단계 동안 1~3분 사이트가 멈춘다(평소 업그레이드와 같다). 나머지 단계 동안은 계속 열려 있다.
- **한 단계씩** 복사해 실행하고 "보여야 하는 것"과 같은지 확인한 뒤 다음으로 간다. 다르면 멈추고 그 단계의 "다르면"을 본다.
- 메모장을 하나 열어 둔다. 1·2·5단계에서 적어 둘 것이 있다. 다 끝나도 **"SELinux 원래 값"은 지우지 말고 이 서버 관리 기록에 남긴다**(nginx 를 걷어낼 때 쓴다).

**1. 지금 상태 확인하고 적어 두기**

```bash
cd /opt/duty_generator
systemctl is-active duty-web duty-worker
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8090/login/
tailscale version
sudo tailscale funnel status
```
보여야 하는 것:
- `active` 두 줄, 그리고 `200`.
- `tailscale version` 의 첫 줄이 `1.52` 이상(예: `1.80.2`).
- `funnel status` 에 `(Funnel on)` 이 붙은 주소 한 줄과 `|-- / proxy http://127.0.0.1:8090`.

**`funnel status` 출력 전체를 메모장에 복사해 둔다**(되돌릴 때 이것과 비교한다).

다르면:
- `active`·`200` 이 아니면 nginx 작업을 하지 말고 웹부터 살린다(`journalctl -u duty-web -n 50`).
- 버전이 1.52 보다 낮거나, `funnel status` 의 주소·경로·포트가 위와 다르면(예: `:8443`, `/` 가 아닌 경로) 멈추고 관리자에게 그 출력을 보낸다.

**2. 새 버전 받기**

```bash
cd /opt/duty_generator
sudo git log -1 --format=%h
```
나온 글자(예: `98ac1fe`)를 **메모장에 "업그레이드 전 버전"으로 적는다.** 그다음 아래 "업그레이드·롤백"의 명령 묶음을 **처음부터 마지막 `systemctl is-active duty-web duty-worker` 줄까지** 한 줄씩 하고(이때 사이트가 1~3분 멈춘다), 여기로 돌아와 아래를 실행한다.

```bash
ls /opt/duty_generator/deploy/
```
보여야 하는 것: `duty-nginx.conf  duty-web.service  duty-worker.service`.
다르면: `git pull` 이 안 된 것이다. 화면에 나온 오류를 관리자에게 보낸다.

> 이 버전부터 상태 점검이 nginx 주소(8008)를 본다. 그래서 6단계를 마치기 전에 다음 점검(5분마다)이 돌면 **"nginx 응답 없음(웹은 정상)" 장애 알림이 한 번** 온다. 정상이다. 6단계가 끝나면 다음 점검 때 "정상으로 돌아왔습니다"가 온다. 중간에 멈추게 되더라도, 웹이 실제로 죽으면 알림 문구가 "웹 응답 없음"으로 바뀌어 다시 오므로 장애를 놓치지 않는다.

**3. nginx 설치**

```bash
sudo dnf install -y nginx
nginx -v
```
보여야 하는 것: 맨 끝에 `Complete!`, 그리고 `nginx version: nginx/1.20.1` 같은 줄(숫자는 달라도 된다).
다르면: `This system is not registered`, `Cannot download repomd.xml` 같은 오류는 서버 패키지 저장소 문제다. 오류 문구를 그대로 관리자에게 보낸다.

**4. 설정 파일 바꾸고 검사** (첫 줄은 패키지 기본 설정을 `nginx.conf.orig` 로 남겨 두는 것이다. 이 단계를 **다시** 할 때는 첫 줄을 건너뛴다 — 다시 하면 남겨 둔 기본 설정이 덮인다)

```bash
sudo cp /etc/nginx/nginx.conf /etc/nginx/nginx.conf.orig
sudo cp /opt/duty_generator/deploy/duty-nginx.conf /etc/nginx/nginx.conf
sudo nginx -t
```
보여야 하는 것(두 줄):
```
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```
다르면: 오류 줄을 그대로 관리자에게 보낸다. 파일을 손으로 고치지 않는다.

**5. SELinux 허용 (nginx 가 8090 의 웹에 붙을 수 있게)**

```bash
getenforce
```
- `Enforcing` 또는 `Permissive` 가 나오면, 먼저 `getsebool httpd_can_network_connect` 결과(`off` 또는 `on`)를 **메모장에 "SELinux 원래 값"으로 적고** 아래를 실행한다. **프롬프트가 다시 나올 때까지 기다린다**(아무 출력 없이 1~3분 걸릴 수 있다. 중간에 Ctrl+C 를 누르지 않는다).
  ```bash
  sudo setsebool -P httpd_can_network_connect 1
  getsebool httpd_can_network_connect
  ```
  보여야 하는 것: `httpd_can_network_connect --> on`.
- `Disabled` 가 나오면 이 단계는 건너뛴다.

**6. nginx 켜고 확인 (부팅 때도 자동으로 켜진다)**

```bash
sudo systemctl enable --now nginx
systemctl is-active nginx
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8008/login/
```
보여야 하는 것: `Created symlink ...` 한 줄(처음이면 나온다), 그리고 `active`, 그리고 `200`.
다르면:
- `active` 가 아니면: `sudo journalctl -u nginx -n 30` 을 관리자에게 보낸다. 그 안에 `Address already in use` 가 있으면 8008 을 다른 프로그램이 쓰고 있는 것이다(`sudo ss -ltnp 'sport = :8008'` 결과도 함께 보낸다).
- `502` → 5단계(SELinux)를 빠뜨렸거나 웹이 꺼져 있다. `getsebool httpd_can_network_connect` 가 `on` 인지, `systemctl is-active duty-web` 이 `active` 인지 본다.
- `000` → nginx 가 8008 을 열지 않았다. `grep -c 8008 /etc/nginx/nginx.conf` 가 `1` 이상인지(4단계 파일이 들어갔는지) 본다.
- 그 밖의 숫자(400·403·504 등)나 위로 해결이 안 되면: 그 숫자와 `sudo tail -5 /var/log/nginx/duty-error.log` 를 관리자에게 보낸다.

여기까지는 사용자에게 아무 변화가 없다(바깥 주소는 아직 8090 으로 바로 간다).

**7. 바깥 주소를 nginx 로 돌리기 (이 순간부터 사용자가 nginx 를 거친다)**

```bash
sudo tailscale funnel --bg --set-path / http://127.0.0.1:8008
sudo tailscale funnel status
```
- 첫 명령은 `Available on the internet: ...` 와 함께 `To disable the proxy, run: tailscale funnel --https=443 off` 같은 안내를 보여 준다. **그 `off` 명령은 치지 않는다**(바깥 공개가 통째로 꺼진다).

보여야 하는 것: 1단계에서 적어 둔 출력과 **같고**, 마지막 줄만 `|-- / proxy http://127.0.0.1:8008` 로 바뀌어 있다.
다르면: 바로 아래 "되돌리기"의 1번을 하고 관리자에게 두 출력을 보낸다.

**8. 바깥에서 확인** — 휴대폰의 **와이파이를 끄고**(LTE/5G), 브라우저의 **시크릿(비공개) 창**으로 당번표 주소를 연다. 아이디·비밀번호를 **직접 넣어 로그인**하고 근무표가 보이면 끝이다.
다르면: 화면에 보이는 숫자나 문구(예: `403`, `502`, `CSRF`)를 적고 "되돌리기"를 한다.

**9. 마무리** — 6단계 뒤 다음 점검(5분마다) 때 장애 알림방에 "정상으로 돌아왔습니다"가 오면(2단계 안내의 알림이 왔었다면) 모두 끝났다. 메모장의 "SELinux 원래 값"은 서버 관리 기록에 옮겨 둔다.

### 되돌리기 (문제가 생겼을 때)

**1. 바깥 주소를 예전처럼 웹으로 바로 보낸다** — 대부분 이것만 하면 된다.

```bash
sudo tailscale funnel --bg --set-path / http://127.0.0.1:8090
sudo tailscale funnel status
```
보여야 하는 것: 1단계에서 적어 둔 출력과 똑같다(`|-- / proxy http://127.0.0.1:8090`). 사이트는 이 직후부터 예전처럼 동작한다.
7단계 전에 문제가 생겼다면 바깥 주소는 아직 8090 이므로 이 명령을 해도 되고 안 해도 된다.

**2. nginx 는 켜 둔다.** 서버 안(127.0.0.1)에서만 열려 있어 켜 둬도 해가 없고, 상태 점검도 정상으로 돈다. **nginx 자체가 안 뜨는 경우에만** 끈다:
```bash
sudo systemctl disable --now nginx
```
끄면 장애 알림에 "nginx 응답 없음(웹은 정상)"이 한 번 온다. 그 뒤에 웹이 실제로 죽으면 "웹 응답 없음"으로 다시 온다. 이 상태로 다음 업그레이드를 하면 아래 "평소 운영"의 nginx 설정 갱신은 건너뛴다.

### 평소 운영

**업그레이드 뒤 nginx 설정 갱신** ("업그레이드·롤백" 묶음을 마친 뒤, nginx 를 켜 둔 서버만):

```bash
cd /opt/duty_generator
sudo cmp deploy/duty-nginx.conf /etc/nginx/nginx.conf && echo 같음
```
- `같음` 이 나오면 할 일이 없다. 끝.
- `differ` 가 나오면 새 버전에서 설정이 바뀐 것이다. 지금 파일을 남겨 두고 바꾼 뒤 검사한다. **`cp` 두 줄은 아무것도 출력하지 않아야 한다**(오류 문구가 나오면 거기서 멈추고 관리자에게 보낸다):
  ```bash
  sudo cp /etc/nginx/nginx.conf /etc/nginx/nginx.conf.bak
  sudo cp deploy/duty-nginx.conf /etc/nginx/nginx.conf
  sudo nginx -t
  ```
  - 두 줄(`syntax is ok`, `test is successful`)이 나오면:
    ```bash
    sudo systemctl reload nginx
    curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8008/login/
    ```
    아무 오류 없이 `200` 이 나오면 끝(끊김 없이 새 설정으로 바뀐다).
  - `nginx -t` 가 두 줄이 아니거나, `reload` 가 오류를 내거나, `200` 이 아니면 **바로 예전 파일로 되돌린다**(그대로 두면 다음 재부팅 때 nginx 가 안 떠 사이트가 끊긴다):
    ```bash
    sudo cp /etc/nginx/nginx.conf.bak /etc/nginx/nginx.conf
    sudo nginx -t
    ```
    - 두 줄이 나오면: `sudo systemctl restart nginx` 후 `curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8008/login/` 가 `200` 인지 확인하고 관리자에게 알린다.
    - 두 줄이 안 나오면: **`restart` 하지 않는다**(지금 돌고 있는 nginx 는 마지막으로 읽어 들인 설정으로 계속 돈다). 그대로 두고 바로 관리자에게 알린다. 재부팅하지 않는다.

그 밖에:
- **nginx 패키지 업데이트**는 서버 정기 업데이트(`sudo dnf update`)에 같이 들어간다. 따로 할 일은 없다.
- **로그**: `/var/log/nginx/duty-error.log`(웹에 못 붙음 등). 접근 로그는 끈다(캘린더 주소에 비밀 토큰이 있다). 오래된 로그는 nginx 패키지가 알아서 정리한다(`/etc/logrotate.d/nginx`).
- **응답 코드 뜻**: `502` = nginx 는 살아 있는데 웹(gunicorn)이 꺼져 있음(`systemctl status duty-web`). `413` = 2MB 넘는 요청.
- **nginx 만 다시 띄우기**: `sudo systemctl restart nginx`. 웹·작업자는 건드리지 않아도 된다.
- **패키지 업데이트 뒤 `/etc/nginx/nginx.conf.rpmnew` 가 생겨도** 무시한다(패키지의 새 기본 설정일 뿐, 쓰이지 않는다). `nginx.conf` 를 그것으로 바꾸지 않는다.
- 앱 안의 요청 가드(`duty/guard.py`)는 그대로 둔다: 로그인 POST 동시 개수 제한(429)은 nginx 가 해 주지 않고, 개발 PC 처럼 nginx 없이 돌 때도 막아 준다.
- nginx 를 서버에서 완전히 걷어낼 때만: 되돌리기 1·2번 뒤 `sudo cp /etc/nginx/nginx.conf.orig /etc/nginx/nginx.conf`. 그리고 5단계에서 적어 둔 "SELinux 원래 값"이 `off` 였을 때만 `sudo setsebool -P httpd_can_network_connect 0` (`on` 이었으면 다른 프로그램이 쓰고 있을 수 있으니 그대로 둔다).

## 외부 공개 (Tailscale Funnel)

```bash
sudo tailscale funnel --bg --set-path / http://127.0.0.1:8008   # nginx 로. gunicorn(8090)으로 바로 보내지 않는다
sudo tailscale funnel status                                     # |-- / proxy http://127.0.0.1:8008
```

- 같은 경로(`/`)에 다시 실행하면 덮어쓴다. `sudo tailscale funnel reset`(또는 `serve reset`)은 **설정 전체를 지운다** — 쓰지 않는다.
- Funnel 에 경로를 더 붙일 때는 `tailscale serve` 가 아니라 `tailscale funnel` 을 쓴다(`serve` 로 붙이면 443 의 바깥 공개가 꺼진다).

## 처음 한 번: 계정 만들기

`/<DUTY_ADMIN_PATH>/` 의 "사용자" 화면이 멤버이자 로그인 계정이다(아이디 = 멤버 코드).
- 첫 어드민은 설치 때 `sudo -u duty .venv/bin/python manage.py createsuperuser` 로 만든다. 아이디·비밀번호 말고 **이름**도 묻는다. 이 계정은 부서가 없어 근무표 대상이 아닌 어드민 전용 계정이고, "스태프 권한"·"슈퍼유저 권한"이 켜져 있어 관리 화면에 들어간다. 기본 알림 규칙은 생기지 않는다(필요하면 알림 화면에서 추가).
- **이어서 바로 (한 번)**: 슈퍼유저는 그것만으로 근무표 관리자가 아니다(마이그레이션이 `createsuperuser` 보다 먼저 돌아 "IT 근무표 관리" 그룹이 비어 있다). `/<DUTY_ADMIN_PATH>/` → "사용자" → 내 계정 → "그룹" 칸에서 **"IT 근무표 관리"** 를 오른쪽으로 옮기고 저장한다. 사이트에 다시 들어가 메뉴에 [회차]·[이력]·[근무표 설정](관제 정의가 있으면 [통계]도)이 보이면 된다. 그 뒤 다른 관리자와 부서 입력 담당자는 근무표 관리자가 사이트 메뉴 [근무표 설정]에서 넣고 뺀다.
- 새 사람: [사용자 추가]에서 아이디·이름·부서·파트·구분을 넣는다(비밀번호 없이 만들어지고 아직 로그인할 수 없다). 근무표 관리자는 사이트 [근무표 설정] → 사람에서 직접 더하고 [계정 발급]한다(아이디는 영문 소문자·숫자·_, 다음 번호가 미리 들어 있다). 관리자 계정(어느 근무표든 관리자인 계정)은 근무표 관리자가 다루지 못하니 여기 관리 화면에서 한다.
- 계정이 털렸다고 의심되면 [계정 발급]으로 초기화한다. 로그인 세션·캘린더 구독 주소·텔레그램 연결·푸시 기기가 모두 끊긴다(본인이 새 비밀번호로 들어와 다시 연결). 근무표 관리자의 [근무표 설정] [비밀번호 초기화]는 비밀번호를 잊은 사람용이라 연결을 남긴다(로그인만 끊긴다). 털림 의심은 슈퍼유저가 이 관리 화면 액션으로 한다.
- 계정 발급: 목록에서 선택 → "계정 발급 / 비밀번호 초기화" 액션 → 화면에 한 번만 보이는 임시 비밀번호(헷갈리는 0·o·1·l·i 없는 영문 소문자·숫자 10자, 띄어쓰기 없음)를 **사람마다 1:1로** 전달한다(단톡방·공유 문서에 올리지 않는다). 자기 계정은 선택해도 빠진다(내 비밀번호는 메뉴의 [비밀번호]). 첫 발급 때 기본 알림 규칙이 생기고, 첫 로그인에서 비밀번호를 바꾸게 한다. 임시 비밀번호는 **발급 뒤 7일 안에** 첫 로그인해야 쓸 수 있다. 지나면 로그인 화면이 "임시 비밀번호의 유효 기간(7일)이 지났습니다…"를 보이고 들이지 않는다([근무표 설정] 계정 열 '임시 비밀번호 만료'). 그 사람에게 다시 발급한다. 결과 화면은 한 번만 보인다(새로 고치면 다시 발급할지 브라우저가 묻는다. 다시 보내면 새 비밀번호가 된다). 근무표 관리자는 [근무표 설정] → 사람에서 같은 일을 한다(발급 전인 사람을 체크해 [선택한 사람 계정 발급], 이미 발급한 사람(첫 로그인 대기 포함)은 그 줄 [고치기 · 비밀번호 · 퇴사] → [비밀번호 초기화], 비밀번호는 그 화면의 빨간 상자에만 한 번 보인다).
- 어드민 전용 계정(근무표에 안 들어감)은 부서를 비워 둔다. 관리 화면에 들어갈 사람(슈퍼유저)은 "스태프 권한"과 "최상위 사용자 권한"(화면 라벨. 슈퍼유저를 뜻한다)을 둘 다 켠다. Django 관리 화면(사용자·부서·근무표·그룹·입력 담당자·휴장일, 계정 발급, 잠금 해제)은 슈퍼유저만 쓸 수 있다(스태프에게 모델 권한을 줘도 들어오지 못한다). 슈퍼유저는 1~2명을 가정한다.
- **근무표 관리자**(회차·생성·배포·통계·이력·지난 날짜 수정)는 그룹으로 정한다: "사용자" → 그 사람 → "그룹" 칸에서 "IT 근무표 관리"를 넣고 뺀다. 근무표 관리자도 사이트 [근무표 설정] → 관리자에서 그 근무표 사람이나 부서 없는 계정을 넣고, 나 자신과 퇴사한 관리자를 뺀다. 재직 중인 다른 관리자를 빼는 일은 여기(사용자 "그룹" 칸)서만 한다. 어느 쪽에서든 **재직 중인 관리자가 하나도 남지 않게는 빼거나 재직을 끌 수 없다**(관리 화면 사용자 편집은 "<근무표> 근무표에 재직 중인 관리자가 남지 않습니다. 먼저 다른 관리자를 넣으세요." 오류. 사용자 지우기(한 명·일괄)는 오류 대신 삭제 확인 화면의 "보호된 객체" 목록에 같은 문구가 나오고 아무것도 지워지지 않는다). "스태프 권한" 체크는 관리자 판정에 쓰이지 않는다.
- 점심 시각은 부서 화면의 "점심 시작"·"점심 끝"(둘 다 넣거나 둘 다 비움). 점심당번 개인 알림·캘린더에 쓰이고, 비우면 점심당번 알림은 날짜 기준 규칙(전날 18시 등)으로만 가고 캘린더 일정은 생기지 않는다.
- 부서 입력 담당자는 근무표 관리자가 사이트 [근무표 설정] → 입력 담당자에서 넣고 뺀다(관리 화면 부서 화면의 "입력 담당자"로도 된다). 그 부서의 입력 그룹 "<부서> 출근표 입력" 멤버가 되고, 그룹은 첫 담당자를 넣을 때 생긴다(같은 이름의 그룹이 이미 있으면 막히니 관리 화면 "그룹"에서 그 그룹 이름을 바꾼다). 담당자가 없는 부서는 근무표 관리자만 입력한다. 부서 화면에서 근무표(새 부서만. 저장한 부서의 근무표는 바꿀 수 없다)와 순서(근무표 화면 부서 필터 순서)도 고른다.
- 사용자·부서를 저장하면 "…가 성공적으로 추가되었습니다. 아래 내용을 수정해야 합니다."가 나온다. Django 기본 문구(뜻은 "아래에서 계속 고칠 수 있습니다")라 오류가 아니다.
- 사람의 부서는 관리 화면 "사용자"에서만 바꾼다. 저장할 때 근무표가 달라졌으면 그 사람의 개인 알림 발송 기록(오늘 이후)을 정리한다(셸 등 다른 길로 바꾸면 이 정리가 빠진다).
- 비밀번호는 항상 [계정 발급] 액션으로 준다. 사용자 편집 화면에는 Django 기본 비밀번호 칸(초기화 버튼)이 없다(그 길로 정하면 첫 로그인 비밀번호 변경·기본 알림 규칙·유효 기간을 거치지 않아 뺐다).
- 슈퍼유저 로그인은 12시간 유지된다(다른 사람은 90일). 관리 화면에서 비밀번호 초기화·봇 토큰·그룹 권한을 바꿀 수 있는 세션이라 짧게 둔다.

## 근무표 추가하기

IT 당번표 말고 근무표를 하나 더 만드는 절차다(예: 시장운영실). 코드 변경 없이 관리 화면 `/<DUTY_ADMIN_PATH>/` 에서 아래 순서대로 한다. 예시 값은 시장운영실 기준(10~13명, 월~금, 근무조 3개 07:30–16:30 / 09:00–18:00 / 11:00–20:00, 한 사람 한 주에 한 근무조, 2주마다 이른 조 ↔ 늦은 조, 점심당번은 07:30 조)이다. 근무조가 5개 이상이거나 장중관제처럼 자동 배정이 필요한 팀은 이 절차로 되지 않으니 개발 담당에게 묻는다.

### 한 번에 만들기(명령)

아래 1~4단계(근무표·근무 정의·부서·사람·근무표 관리자)를 명령 하나로 한다. 하나라도 문제가 있으면 아무것도 만들지 않는다. 백업을 먼저 뜨는 것은 같다(아래 "시작 전에").

명단은 실명이라 운영자 자기 홈에 두고 남이 못 읽게 한 뒤 표준 입력(`--people -`)으로 넘긴다. `<` 는 운영자 셸이 여니 duty 사용자는 파일을 읽지 않는다. 성공하든 실패하든 끝나면 지운다.

```bash
install -m 600 /dev/null ~/mops.txt   # 나만 읽는 빈 파일을 먼저 만든다(실명을 적기 전에)
nano ~/mops.txt          # 한 줄에 이름 하나
sudo -u duty .venv/bin/python manage.py add_board mops 시장운영실 \
    --shifts 07:30-16:30,09:00-18:00,11:00-20:00 --lunch 11:30-12:30 \
    --people - --admin <근무표 관리자 아이디> < ~/mops.txt
rm ~/mops.txt            # 성공·실패와 상관없이
```

- 명단: UTF-8 텍스트, 한 줄에 이름 하나. 빈 줄과 `#`로 시작하는 줄은 건너뛴다. 이름 규칙은 아래 3단계와 같다. 저장소 안이나 `/tmp` 에 두지 않는다.
- 만드는 것: 근무표(작성 중·마감 끔, 단계 입력 중 → 확정 → 배포됨)와 관리 그룹, `--shifts` 순서대로 근무조 1~4(이름은 시작 시각, 기본 알림 대상 켬, 최대 4개), 점심당번 정의(시각 없음), 부서 하나(코드·이름은 근무표와 같다, 출근조 전부, 점심 시각은 `--lunch` 또는 비움), 사람마다 계정(아이디 `mops01`, `mops02`…는 명단 순서, 100명부터 세 자리, 구분 직원, 비밀번호 없음). `--admin` 은 이미 있는 사용자를 근무표 관리 그룹에 넣는다(빼면 4단계를 손으로).
- 코드는 영문 소문자로 시작하는 영문 소문자·숫자 **8자 이내**(부서 코드로도 쓴다). 같은 코드·이름의 근무표, 이미 있는 이름·아이디(대소문자 구분 없음)는 막는다. 오류에는 명단의 줄 번호와 까닭만 나온다(이름은 보이지 않으니 줄 번호로 파일을 본다).
- 끝나면 요약(이름 없이 인원과 아이디 범위)이 나온다. 이어서 계정 발급(사용자 목록 → 액션 "계정 발급 / 비밀번호 초기화", 또는 근무표 관리자가 [근무표 설정] → 사람에서 체크 → [선택한 사람 계정 발급])과 5단계(첫 회차)를 한다.
- 아이디는 임시다. 바꾸려면 관리 화면 → 사용자에서 고친다(계정 발급 전에 하는 편이 낫다).
- 근무조 이름·시각, 점심 시각, 사람 추가 등 **만든 뒤 바꾸는 일은 아래 단계의 관리 화면에서** 한다. 점심당번이 필요 없는 팀은 만든 뒤 근무표 화면에서 점심당번 줄의 "사용"을 끈다(확정할 때 점심당번을 정하지 않는다).

### 시작 전에

- 슈퍼유저 계정으로, **PC 브라우저(가로 1200px 이상)**에서 한다. 휴대폰에서는 관리 화면의 근무 정의 표가 넘쳐 시작·끝·사용 칸이 화면 밖에 있다. 5단계의 출근표 입력도 PC 를 권한다(휴대폰에서는 근무조 열이 옆으로 밀린다).
- 백업을 먼저 뜬다: `sudo -u duty .venv/bin/python manage.py backup` (위 "백업·복원").
- 그 팀에 미리 물어 둔다: 근무표 이름, 근무조 이름과 시각, 점심 시각(모르면 비워 둔다), 근무표 관리자(근무표를 만들고 배포하는 사람), 사람 명단(아이디로 쓸 멤버 코드·이름·파트), 처음 배포할 기간.
- **근무표는 지울 수 없고 코드는 저장한 뒤 바꿀 수 없다**(회차 단계는 나중에도 근무표 화면이나 [근무표 설정]에서 고친다). 근무표를 만들면 모든 사람의 근무표 고르기 목록에 들어간다(근무표가 둘 이상이 되면 [주간]·[월간] 앞에 [근무표: ○○] 단추가 보인다). 첫 저장 전에 아래 값을 한 번 더 확인한다. 연습은 개발 PC 에서 가짜 이름으로 먼저 해 본다.

### 1. 근무표와 근무 정의 (관리 화면 → 근무표 → [근무표 추가])

한 화면에서 근무표와 근무 정의를 **함께** 넣고 저장한다. (화면에 따라 근무조를 "출근조"라고도 부른다. 같은 것이다.) 근무 정의 없이 저장하면 "켜진 근무조가 하나 이상 있어야 합니다."로 막힌다.

| 칸 | 넣을 값 (시장운영실 예) | 비고 |
|---|---|---|
| 코드 | `mops` | 영문 소문자로 시작하는 영문 소문자·숫자 16자 이내. 주소의 `?board=mops` 에 쓰인다. 저장 뒤 못 바꾼다 |
| 이름 | 시장운영실 | 근무표 고르기 목록·구역 이름표·제목에 보이는 이름 |
| 작성 중 단계 사용 / 마감 단계 사용 | 둘 다 끈다 | "회차 단계" 묶음. 끄면 그 단계를 건너뛴다(IT 는 둘 다 켬). 나중에 [근무표 설정]에서도 바꿀 수 있지만 진행 중인 회차에 바로 반영되니 처음에 정한다 |
| 단계 이름 | 취합 중 이름 "입력 중", 생성됨 이름 "확정"(나머지 그대로) | 회차 화면 단계·버튼 이름이 된다("입력 중"·[확정]·[확정 취소]). 다섯 이름은 서로 달라야 한다 |

아래 "근무 정의"는 처음에 줄이 없다. [근무 정의 더 추가하기]를 네 번 눌러 네 줄을 만들고 아래처럼 채운다. "키" 목록에서는 근무조 1·2·3 과 점심당번만 고른다(**관제 1~10 은 장중관제 전용이라 고르지 않는다**. 근무조 4·점심당번은 목록에서 관제 10 아래에 있다).

| 키 | 이름 | 시작 | 끝 | 기본 알림 대상 | 사용 |
|---|---|---|---|---|---|
| 근무조 1 | 07:30 | 07:30 | 16:30 | 켬 | 켬 |
| 근무조 2 | 09:00 | 09:00 | 18:00 | 켬 | 켬 |
| 근무조 3 | 11:00 | 11:00 | 20:00 | 켬 | 켬 |
| 점심당번 | 점심당번 | (비움) | (비움) | 끔 | 켬 |

- "근무조 1~4"는 이름일 뿐이다. 이른·가운데·늦은 조는 **시작 시각**으로 정해지고 화면에도 시작 시각 순으로 보인다. "이름"은 근무표 화면·CSV 열 머리에 그대로 보이니 그 팀이 부르는 말로 짧게 쓴다(위처럼 시각을 이름으로 써도 된다. 그러면 캘린더 일정 제목이 "07:30 출근 07:30~16:30"처럼 시각이 두 번 보인다).
- 이름은 근무표 안에서 겹치면 안 되고 `date`·`day` 가 아니어야 하며 `(` 와 줄바꿈을 쓸 수 없다. 켜진 근무조끼리 시작 시각이 달라야 하고 시작이 끝보다 일러야 한다(밤을 넘기는 근무는 안 된다).
- **점심당번**은 시각을 비운다(넣으면 "점심당번은 시각을 비웁니다(점심 시각은 부서마다 정합니다)."). 확정할 때 날마다 가장 이른 근무조(07:30)에 사유 없이 나온 사람 전원이 점심당번이 된다. 점심당번이 필요 없는 팀은 이 줄을 넣지 않는다.
- **기본 알림 대상**: 계정을 처음 발급할 때 생기는 기본 알림(전날 18시, 시작 2시간 전, 텔레그램)이 켠 근무조에 걸린다. 알림은 **켠 근무조에 들어간 날에만** 온다. 2주마다 근무조가 바뀌는 팀은 위처럼 근무조 1·2·3 을 모두 켠다(07:30 만 켜면 09:00·11:00 주에는 기본 알림이 오지 않는다). 점심당번은 켜지 않아도 된다(점심당번 알림이 필요한 사람은 각자 [알림·캘린더]에서 더한다). 하나도 켜지 않으면 기본 알림이 생기지 않는다. 알림을 쓰는 팀인지 물어보고 정한다. 이미 발급한 계정의 규칙은 이 칸을 바꿔도 그대로다.
- "자격 근무조"·"자격 구분"은 장중관제 칸 전용이라 비워 둔다.
- [저장]하면 관리 그룹 **"시장운영실 근무표 관리"** 가 저절로 생긴다. 저장 뒤 근무표 화면의 "관리 그룹" 칸에 그 그룹 링크가 보인다.

### 2. 부서 (관리 화면 → 부서 → [부서 추가])

| 칸 | 넣을 값 | 비고 |
|---|---|---|
| 코드 | `mops` | 8자 이내. 저장 뒤 못 바꾼다 |
| 이름 | 시장운영실 | 모든 근무표를 통틀어 겹치지 않게 |
| 근무표 | 시장운영실 | 저장 뒤 못 바꾼다 |
| 순서 | 99 (그대로) | 근무표 화면 부서 필터 순서. 부서가 하나라 그대로 둔다 |
| 가능한 출근조 | 근무조 1·2·3 모두 체크 | 부서 추가 화면에서는 근무표를 고르기 전이라 "근무조 1~4"로 보인다(저장 뒤에는 07:30 처럼 이름으로). 근무조 4 는 체크하지 않는다. 이 근무표에 켠 근무조만 저장된다 |
| 점심 시작 / 점심 끝 | 팀에 물어 넣는다(예: 11:30 / 12:30) | 둘 다 넣거나 둘 다 비운다. 비우면 점심당번 개인 알림은 날짜 기준 규칙(전날 18시 등)으로만 가고 캘린더 일정은 생기지 않는다. 나중에 넣어도 된다 |
| 입력 담당자 | 비워 둔다 | 비우면 근무표 관리자만 입력한다. 담당자가 필요하면 근무표 관리자가 나중에 [근무표 설정]에서 넣는다 |

### 3. 사람 (관리 화면 → 사용자 → [사용자 추가])

근무표를 만든 뒤에는 근무표 관리자가 [근무표 설정] → 사람 → '사람 추가'에서 넣어도 된다(아래 칸 규칙이 같고, 구분은 장중관제가 없는 근무표면 늘 직원).

사람마다 한 번씩:

| 칸 | 넣을 값 |
|---|---|
| 아이디 | 멤버 코드(로그인 아이디). 대소문자만 다른 아이디는 만들 수 없다 |
| 이름 | 근무표에 보일 이름. 모든 근무표를 통틀어 겹치지 않게(동명이인은 구별되게 적는다). `>` `,` 를 쓸 수 없고 (휴가)·(출장)·(교육)으로 끝날 수 없다 |
| 부서 | 시장운영실 |
| 파트 | 비워도 된다 |
| 구분 | **직원** (장중관제가 없는 근무표의 사람은 모두 직원. 비우면 "부서가 있으면 구분(직원·개발자)을 고르고…"로 막힌다) |

다 넣었으면 계정을 발급한다: 사용자 목록에서 그 사람들을 체크 → 액션 "계정 발급 / 비밀번호 초기화" → [실행]. 화면에 한 번만 보이는 임시 비밀번호를 **사람마다 1:1로** 전달한다(위 "처음 한 번: 계정 만들기"). 첫 로그인에서 비밀번호를 바꾸게 한다.

### 4. 근무표 관리자 (관리 화면 → 사용자)

- **근무표 관리자**: 사용자 → 그 사람 → "그룹" 칸에서 "시장운영실 근무표 관리"를 오른쪽(선택된 그룹)으로 옮기고 저장한다. 관리자가 시장운영실 사람이 아니어도 되고(슈퍼유저 본인 포함), 둘 이상이어도 된다. 슈퍼유저라도 이 그룹에 넣지 않으면 시장운영실 회차를 만들 수 없다. 관리자에게는 메뉴 [출근표 입력]·[회차]·[이력]·[근무표 설정]과 도움말 "회차 운영(단계·출근표·생성·배포)"·"근무표 설정"이 보인다. 그 뒤 일상 작업(관리자 더하기, 입력 담당자, 근무 정의·부서 출근조·점심 시각)은 근무표 관리자가 [근무표 설정]에서 한다. [출근표 입력]은 회차 화면의 [표 입력]과 같은 화면이다(입력 중인 회차가 없으면 "입력 중인 회차가 없습니다"만 보인다). 관리자 사용법 영상은 IT 화면으로 찍어서 장중관제가 있는 근무표의 관리자에게만 보인다(시장운영실 관리자는 글 도움말을 따른다).
- 관리 화면 "그룹"은 이름·멤버를 보기만 한다(멤버는 사용자 화면의 "그룹" 칸이나 사이트 [근무표 설정]에서 고친다). **그룹 "이름" 칸은 고치지 않는다**: 근무표 이름을 바꿀 때 따라 바뀌는 이름이라 여기서 바꾸면 근무표 이름과 어긋난다. [삭제]는 누르지 않는다(근무표의 관리 그룹은 지울 수 없게 막혀 있다).

### 5. 첫 회차와 배포 (사이트, 근무표 관리자)

관리자 계정으로 사이트에 들어가 메뉴 [회차] → [+ 새 회차]에서 이름·시작일·종료일을 넣고 [만들기](관리하는 근무표가 둘 이상이면 "근무표"도 고른다). 회차는 바로 **입력 중**이 된다. 이어서 [표 입력] → [표 저장] → [확정] → [배포…] 순이다. 화면마다 할 일은 사이트 [도움말]의 "회차 운영"에 있다.

- 입력 표의 칸은 이름이 많으면 줄을 바꿔 다 보인다. 칸에서 Enter 를 누르면 표가 저장된다.
- [확정]을 누르면(출근표가 빈 날이 있으면 그 날 수를 먼저 묻는다) "'확정' 상태로 바꿨습니다. 근무표 화면에는 배포한 뒤에 보입니다."가 나온다. 출근표가 비어 있는 날이 있으면 바로 아래 경고("출근표가 비어 있는 날이 있습니다: …")를 보고 [배포…]로 간다.
- 배포 화면의 "덮어쓰기 시작일"은 이 회차로 근무표를 바꾸기 시작할 날이다. 처음 채워진 값은 **오늘**(회차 시작일이 오늘보다 뒤면 회차 시작일)이고, 그보다 앞날의 이 회차 데이터는 배포할 때 **지워진다**. 그래서 [배포]를 누르기 전에 꼭 본다:
  - **회차 시작일이 오늘 이전인 첫 배포**(시작일이 지난 회차를 이제 배포할 때)는 "덮어쓰기 시작일"을 **회차 시작일**로 바꾸고 [범위 다시 보기]를 누른다. "덮어쓰기 범위"가 회차 시작일부터이고 "시작일 이전의 이 회차 데이터는 버립니다."가 **보이지 않는 것**을 확인한 뒤 [배포]를 누른다.
  - 회차 시작일이 오늘이거나 앞으로의 날이면 처음 값이 회차 시작일이라 그대로 [배포]해도 된다(위 문장이 보이지 않는다).
  - 이미 배포한 근무표의 앞부분을 남기고 뒤만 바꿀 때만 시작일을 뒤로 고르고 [범위 다시 보기]. 이때는 위 문장이 보이는 것이 맞다.
  - "사라지는 근무 변경"은 그 범위에서 배포 뒤 칸으로 바꾼 것이 덮어써지는 건수다(첫 배포는 0건).
- 배포한 뒤 근무표 화면에서 날마다 "점심당번" 줄에 07:30 조에 사유 없이 나온 사람이 모두 들어갔는지 본다.

- **[2주 전 기준으로 채우기]**는 2주 전 그 주의 근무를 보고 이른 조 ↔ 늦은 조를 맞바꿔 채운다(근무조가 3개일 때만 보인다). 2주 전이 회차 기간 밖이면 **배포된 근무표**를 본다. 2주 전 그 주에 근무가 아무도 없으면(이전 근무표가 배포돼 있지 않은 첫 회차의 첫 두 주 등) "2주 전 그 주에 근무가 없어 채울 수 없습니다…"로 채우지 않는다. 첫 회차의 첫 두 주는 손으로 넣고(엑셀 근무표를 보고), 셋째 주부터는 같은 회차 안의 두 주 전을 보고 채운다. 다음 회차부터는 앞 회차가 배포돼 있으면 그대로 쓴다. 채우기는 보여 주기만 하니 확인한 뒤 [표 저장]을 누른다.
- **[지난주와 같게]**는 지난주 같은 요일을 옮긴다. 지난주에 휴장일·근무 없음이었던 요일은 옮길 것이 없어 **빈칸으로 남는다**("N칸을 채웠습니다"의 수에도 들어가지 않는다). 그 요일은 직접 채우거나 [2주 전 기준으로 채우기](요일과 상관없이 그 주 전체를 채운다)를 쓴다. 회차 화면의 "⚠ 출근표가 비어 있는 날" 경고로도 확인한다.
- 휴가·출장·교육은 칸에 "이름(휴가)"처럼 적는다. 휴장일은 입력 표에서 잠겨 근무자 0명이 된다(모든 근무표 공통, 위 "휴장일"). 시장운영실만 쉬는 날은 근무표 화면 날짜 칸의 [메모]에서 "근무 없음"으로 적는다(그날 사람마다 한 줄씩 [이력]에 "→ (없음)"으로 남는다).
- 배포한 뒤 휴가가 생기면 근무표 칸을 눌러 근무 변경 창의 [사유 저장]으로 붙인다. 07:30 조 사람에게 붙이면 "…은(는) 그날 점심당번 칸에 남아 있습니다"가 뜬다(확정 때 정한 점심당번은 저절로 바뀌지 않는다). 그날 "점심당번" 칸을 눌러 그 사람을 다른 사람으로 바꾸거나, 남은 07:30 인원으로 충분하면 To 에서 "(없음 — 빼기만)"을 골라 뺀다. 그대로 두면 그 사람은 취소선으로 보이고 점심당번 알림은 가지 않는다.
- 근무표 칸은 근무표 관리자뿐 아니라 **시장운영실 사람도 오늘 이후 날짜를 바꿀 수 있다**(IT 와 같은 규칙, 모두 [이력]에 남는다). 지난 날짜는 관리자만 바꾼다.
- 주 메모(특이사항)·달 메모(본부 점심 등)는 근무표 관리자가 근무표 화면의 [메모]로 적는다.
- 배포한 뒤 근무표 화면의 [근무표: ○○] 단추를 눌러 "시장운영실"에 체크하고 [보기]를 눌러 보이는지(되돌릴 때는 [내 근무표만 보기]), 시장운영실 사람으로 로그인했을 때 처음부터 시장운영실이 보이는지 확인한다.

### 운영 중에 바꾸면

| 바꾸는 것 | 어디서 | 어떻게 되나 |
|---|---|---|
| 근무표 이름 | 근무표 화면 "이름" | 근무표 고르기 목록·구역 이름표·제목이 바뀌고 관리 그룹 이름도 "<새 이름> 근무표 관리"로 같이 바뀐다(멤버는 그대로). 같은 이름의 근무표·그룹이 있으면 이름 칸 오류로 막힌다 |
| 부서 이름 | 부서 화면 "이름" | 부서 이름이 바뀌고, 입력 그룹이 있으면 그 이름도 "<새 이름> 출근표 입력"으로 같이 바뀐다(같은 이름의 그룹이 있으면 막힌다) |
| 근무 정의 이름·시각 | 근무표 화면 근무 정의 줄 또는 [근무표 설정] → 근무 정의와 부서 | 근무표 화면(지난 날짜 포함)·알림 문구·캘린더 일정이 새 이름·시각을 쓴다. 발송 창이 열린 알림이 한 번 다시 나가고, "N분 전" 알림 시각이 새 시각을 따라 옮겨 간다. 예전에 내려받은 CSV 는 열 이름이 맞지 않는다. 두 줄의 이름을 맞바꿀 때는 한 줄씩(임시 이름을 거쳐) 저장한다(아래 "운영 메모") |
| 근무조를 그만 씀 | 근무 정의 줄의 "사용" 끄기 | 새 입력 표·CSV 열·부서 출근조·알림 규칙 선택지에서 빠진다. 지난 근무표·기록에는 이름이 그대로 남는다. 켜진 근무조가 하나도 없게 되거나 부서에 켜진 출근조가 남지 않으면 막힌다(부서의 출근조를 먼저 바꾼다). 켜진 근무조가 3개가 아니면 [2주 전 기준으로 채우기]가 사라진다 |
| 근무조를 새로 씀 | [근무 정의 더 추가하기] 또는 [근무표 설정]의 빈 "새 근무 정의" 칸 | 남은 키(근무조 1~4 중 안 쓴 것)로 줄을 더해 저장하고, 부서 "가능한 출근조"에도 체크해 한 번 더 저장한다([근무표 설정]은 체크하지 않은 근무조를 경고하고 [부서 저장]을 보인다). 부서에서 근무조를 뺄 때 배포 전 회차에 그 출근표가 있으면 [근무표 설정]이 행 수를 보이고 [그래도 저장]을 한 번 더 누르게 한다 |
| 저장한 근무 정의 지우기·키 바꾸기 | — | 안 된다(지우기 칸이 없고 키 칸이 잠긴다). "사용"을 끄고 새 줄을 더한다 |
| 점심 시각 | 부서 화면 "점심 시작"·"점심 끝" 또는 [근무표 설정]의 부서 칸 | 점심당번 개인 알림·캘린더 일정 시각이 바뀐다. 비우면 시각 기준 알림·캘린더 일정에서 점심당번이 빠진다 |
| 회차 단계 | 근무표 화면 "회차 단계" 또는 [근무표 설정] 맨 아래(접힌 칸) | 진행 중인 회차의 단계 이름·버튼이 바로 바뀐다. 단계를 끄면 그 단계에 있던 회차는 저장 뒤 안내대로 회차 화면의 "다른 상태로 옮기기"로 옮긴다 |
| 코드, 부서의 근무표·코드 | — | 저장 뒤 바꿀 수 없다(읽기 전용). 근무표는 지울 수도 없으니 잘못 만들었으면 더 손대지 말고 개발 담당에게 묻는다 |
| 관리 그룹 이름 | — | 그룹 화면에서 직접 바꾸지 않는다. 근무표 이름을 바꾸면 따라 바뀐다. 그룹 화면에서 바꾸면 근무표 이름을 다시 바꿀 때까지 어긋난 채로 남는다. 관리 그룹은 지울 수 없다 |
| 관리자 교체 | [근무표 설정] → 관리자(넣기, 나 자신·퇴사자 빼기) 또는 사용자 "그룹" 칸(재직 중인 다른 관리자 빼기) | 그날부터 새 관리자가 회차·메모·지난 날짜 수정·설정을 한다. 재직 관리자가 하나도 남지 않게는 어디서도 뺄 수 없다(새 관리자를 먼저 넣는다) |
| 퇴사·전입 | [근무표 설정] → 사람 → 그 줄 [고치기 · 비밀번호 · 퇴사](발급 전이면 [고치기 · 퇴사]) → [퇴사] / '사람 추가'(관리자 계정은 아래 "관리자 퇴사") | 로그인과 캘린더·텔레그램·푸시 연결이 모두 끊긴다. 오늘 이후 이미 배정된 근무는 남으므로(퇴사 때 목록이 나온다) 근무표·입력 표에서 다른 사람으로 바꾼다. 되돌리려면 '퇴사한 사람' → [다시 재직] → [계정 발급]. 전입·인사이동(부서·근무표 옮기기)은 슈퍼유저가 사용자 "부서"에서(그 사람의 개인 알림 발송 기록이 정리된다) |
| 공동 관리자 들이기 | [근무표 설정] | 사람 추가 → [계정 발급] → 관리자 칸에서 [넣기]. 넣은 뒤에는 관리자 계정이라 사람 칸에서 고칠 수 없다(그 전에 이름을 확인한다) |
| 관리자 퇴사 | [근무표 설정] → 관리자, 그 뒤 사람 | 그 사람이 스스로 관리자 칸에서 나를 [빼기] → 다른 관리자가 사람 칸에서 [퇴사]. 스스로 뺄 수 없으면 슈퍼유저가 관리 화면 사용자 "그룹"에서 빼고 "재직"을 끈 뒤, 사용자 목록에서 그 사람을 골라 [계정 발급 / 비밀번호 초기화] 액션으로 텔레그램·푸시·캘린더 연결도 끊는다(재직만 끄면 로그인과 캘린더 피드는 막혀도 텔레그램·푸시 연결 행은 남는다. 액션이 보여 주는 임시 비밀번호는 전하지 않고 버린다. 재직이 꺼져 있어 로그인되지 않고, 나중에 [다시 재직]하면 그 비밀번호도 쓸 수 없게 된다) |

## 업그레이드·롤백

지금 버전을 먼저 적어 둔다(롤백할 때 쓴다).

```bash
cd /opt/duty_generator
sudo git log -1 --format=%h                  # 지금 버전(적어 둔다)
sudo systemctl stop duty-web duty-worker
sudo -u duty .venv/bin/python manage.py backup   # data/backups/db-YYYYMMDD-HHMMSS.sqlite3 (경로가 출력된다, 적어 둔다)
sudo git pull --ff-only                      # 특정 버전이면: sudo git fetch && sudo git checkout <버전>

sudo -u duty .venv/bin/python manage.py migrate   # 무언가 적용됐으면(DB 구조 변경) 롤백 때 DB 복원이 필요하다
```

- **롤백**: 위와 같은 순서에서 `git pull` 대신 `sudo git checkout <적어 둔 버전>`. 업그레이드 때 `migrate` 가 무언가 적용했으면 `sudo -u duty .venv/bin/python manage.py migrate` 대신 `sudo -u duty .venv/bin/python manage.py restore <업그레이드 전에 만든 백업>`(아래 "백업·복원")을 한다 — 복원은 백업의 마이그레이션이 지금 코드와 같아야 받아 주므로, 코드를 먼저 되돌린 뒤에 한다.
- **근무표 일반화 1단계로 올릴 때 (한 번)**: `migrate` 가 데이터를 옮긴다. IT 근무표와 근무 정의(지금 값 그대로), "IT 근무표 관리" 그룹(지금 "스태프 권한"이 켜진 사람), 부서마다 "<부서> 출근표 입력" 그룹(지금 입력 담당자), 장중관제 행 변환, 지금 슈퍼유저를 모든 새 그룹의 그룹 관리자로. 근무표가 비어 있는 회차는 IT 근무표로 채우고, 근무표가 비어 있는 부서가 남아 있으면 그 부서 코드를 알려 주며 멈춘다(0016). 같은 이름의 그룹이 이미 있으면 `migrate` 가 그 이름을 알려 주며 멈춘다. 그러면 위 "롤백"대로 되돌리고, 사이트를 켠 뒤 관리 화면 "그룹"에서 그 그룹 이름을 바꾸고 업그레이드를 처음부터 다시 한다. 이 버전부터 관리자 지정은 그룹으로 한다("처음 한 번: 계정 만들기"). "스태프 권한" 체크는 관리자 판정에 쓰이지 않는다(관리 화면 출입에만, 슈퍼유저와 함께).
  - 부서 없는 일반 계정은 근무표가 없어 이제 근무를 바꿀 수 없다(보기만). 관리 그룹 멤버면 그대로 고친다.
  - 사용자의 근무표가 바뀌었다 돌아오면(예: IT → 부서 없음 → IT) 아직 시작 전인 개인 알림이 한 번 더 갈 수 있다.
  - 관리 화면 "그룹": 목록 화면에 이름·멤버가 보이고, 그룹 화면에서는 이름만 고친다(멤버는 사용자 화면의 "그룹" 칸에서). 그룹 관리자는 보기만 한다.
  - 업그레이드 전 확인(읽기 전용, 운영자가 실행): 시트에서 가져온 옛 회차 기간 안에 행이 하나도 없는 평일(평일 휴장일)이 있으면, 업그레이드 뒤 그날은 "근무표 없음" 대신 빈 칸으로 보인다(필요하면 넣기로 채운다). 아래가 그런 날을 회차 번호와 함께 보여 준다(없으면 아무것도 안 나온다).
    `sudo -u duty sqlite3 -readonly data/db.sqlite3 "WITH RECURSIVE d(pid, day, last) AS (SELECT id, start_date, end_date FROM duty_period WHERE status='published' UNION ALL SELECT pid, date(day, '+1 day'), last FROM d WHERE day < last) SELECT pid, day FROM d WHERE strftime('%w', day) NOT IN ('0','6') AND NOT EXISTS (SELECT 1 FROM duty_commute c WHERE c.period_id = pid AND c.date = day) ORDER BY day;"`
- **근무표 일반화 2단계로 올릴 때 (한 번, 되돌리기는 업그레이드 전 백업 복원으로만)**: `pip install -r requirements.lock` 이 휴장일 라이브러리 `holidays` 를 새로 깐다. `migrate` 가 사유·메모·휴장일 표, IT 점심당번 정의, IT 부서 점심 시각 11:30~12:30 을 넣고, 업그레이드한 날(포함) 이후의 배포됨·생성됨 회차에서 새벽 근무자를 점심당번으로 채운다(기록·알림 없음). 기존 회차는 휴장일을 건너뛰지 않는다(이름만 보인다). 이후 새로 만드는 회차부터 건너뛴다.
  - 업그레이드 전 확인(읽기 전용): 이름이 (휴가)·(출장)·(교육)으로 끝나는 계정이 있으면 `migrate` 가 멈춘다(0018). 아래가 그런 계정의 아이디를 보여 준다(없으면 아무것도 안 나온다). 있으면 업그레이드 전에 관리 화면에서 이름을 바꾼다. 업그레이드 중에 멈췄으면 위 "롤백"대로 되돌린 뒤 바꾸고 처음부터 다시 한다.
    `sudo -u duty sqlite3 -readonly data/db.sqlite3 "SELECT username FROM duty_user WHERE name LIKE '%(휴가)' OR name LIKE '%(출장)' OR name LIKE '%(교육)';"`
  - `migrate` 를 거꾸로(`migrate duty 0021` 등) 돌려 되돌리지 않는다. 2단계 마이그레이션은 되돌릴 데이터가 있으면 거꾸로 돌기를 거부한다: 0018(휴장일이 있으면), 0019(메모), 0020(사유. 배포 취소 정보의 출근표 행 여섯째 칸 사유도 본다), 0022(점심당번 배정·기록·발송 기록, 배포 취소 정보의 점심당번 행, 점심당번을 고른 알림 규칙·캘린더·근무표 필터). 0022 는 그런 데이터가 없을 때만 IT 근무표의 점심당번 정의와 IT 부서의 점심 시각을 지우고 내려가며, 다른 근무표에 점심당번 정의나 부서 점심 시각이 있으면 거부한다. 문제가 생기면 위 "롤백"(코드 되돌리기 + `restore`)만 쓴다.
  - **IT 보고서 알림이 한 번 다시 나간다**: 보고서 끝에 "점심당번 …" 줄이 붙어 내용이 바뀌므로, 업그레이드한 날 이미 받은 보고서 중 발송 창이 아직 열린 것이 한 번 더 간다(예정된 동작). 개인 알림 문구는 그대로다(점심당번 알림은 새로 생긴다).
  - 작업자가 켜지면 첫 바퀴에 휴장일을 채운다. 관리 화면 "휴장일"에 올해·내년 공휴일과 12/31 이 보이면 된다. 아래 "휴장일"대로 임시공휴일을 더한다.
- **근무표 일반화 3단계로 올릴 때**: 마이그레이션이 없다(업그레이드 절차 그대로, `migrate` 는 "No migrations to apply"). 바뀌는 것: 관리 화면 "근무표"에서 근무표·근무 정의를 추가·편집한다(저장한 정의는 지우거나 키를 바꾸지 못하고 '사용'을 끈다, code·입력 방식은 만든 뒤 못 바꾼다, 직접 입력 근무표에는 부서 하나). 관리 화면 "그룹"에서 그룹 관리자를 정하면 그 사람에게 메뉴 [그룹]이 생긴다(1단계 마이그레이션이 지금 슈퍼유저를 모든 그룹의 그룹 관리자로 넣어 두었으므로 슈퍼유저에게도 [그룹]이 보인다). 새 부서의 출근조는 "근무조 1~4"로 고르고 고른 근무표에 있는 근무조만 저장된다. 저장된 부서의 코드는 읽기 전용이 된다. 근무표·부서 이름을 바꾸면 그 관리 그룹·입력 그룹 이름도 같이 바뀐다(같은 이름의 그룹이 있으면 막는다). 직접 입력 근무표의 회차 화면(입력 중 → 확정 → 배포됨)과 채우기 버튼은 직접 입력 근무표가 생길 때(4단계)부터 보인다. IT 화면·알림은 그대로다.
- **근무표 통합 1단계로 올릴 때 (한 번, 공지 없음)**: `migrate` 가 0023 을 적용한다. 보이는 변화는 없다(IT·시장운영실 회차 화면·버튼·문구·알림 그대로). 관리 화면 "근무표"의 "입력 방식" 칸이 "회차 단계"(작성 중 단계 사용·마감 단계 사용·단계 이름 다섯)로 바뀐다(저장된 근무표에서는 읽기 전용): 옛 직접 입력 근무표는 둘 다 끔·취합 중 "입력 중"·생성됨 "확정", IT 는 둘 다 켬·지금 이름 그대로. 입력 그룹은 새로 생기지 않는다. "직접 입력 근무표는 부서 하나" 제한이 없어진다.
  - 업그레이드 전 확인(읽기 전용, 멈출 일은 없다): 근무표별 입력 방식과 상태별 회차 수를 적어 둔다(업그레이드 뒤 대조용).
    `sudo -u duty sqlite3 -readonly data/db.sqlite3 "SELECT b.code, b.input_mode, p.status, COUNT(p.id) FROM duty_board b LEFT JOIN duty_period p ON p.board_id = b.id GROUP BY 1, 2, 3;"`
  - 업그레이드 뒤 대조(읽기 전용): 근무표·상태·회차 수가 위와 같고, `direct` 였던 근무표는 `0|0|입력 중|확정`, `collect` 였던 근무표는 `1|1|취합 중|생성됨` 이어야 한다.
    `sudo -u duty sqlite3 -readonly data/db.sqlite3 "SELECT b.code, b.use_draft, b.use_close, b.step_collecting, b.step_generated, p.status, COUNT(p.id) FROM duty_board b LEFT JOIN duty_period p ON p.board_id = b.id GROUP BY 1, 2, 3, 4, 5, 6;"`
  - 업그레이드 전 확인 ②(읽기 전용, 참고용): 장중관제 정의를 켜 두었거나 관제 배정이 남은 직접 입력 근무표. 1단계에서는 이런 근무표도 지금 화면 그대로다([확정]·[확정 취소]만). 2단계(데이터 기준)부터 경우에 따라 달라진다 — 켜진 관제 정의 수가 0이 아니면 [장중관제 생성]·[재생성]·[생성 방식]이 생기고 배정이 있는 회차에는 배정 횟수 표가 보이며, 정의는 0이고 관제 배정 행만 남았으면 버튼은 그대로이고 배정 횟수 표와 [확정 취소] 확인창 글만 바뀐다. 여기서는 결과를 참고로 적어 두기만 하고, 2단계를 올리기 직전에 같은 확인을 다시 돌려(작성 중·마감을 둘 다 끈 근무표 기준) 그때 값으로 공지와 진행을 정한다(아래 "근무표 통합 2단계로 올릴 때"). 근무표마다 `코드|켜진 관제 정의 수|관제 배정 행 수`, 모두 0 이면 해당 없음.
    `sudo -u duty sqlite3 -readonly data/db.sqlite3 "SELECT b.code, (SELECT COUNT(*) FROM duty_boardshift s WHERE s.board_id = b.id AND s.active = 1 AND s.key LIKE 'slot%'), (SELECT COUNT(*) FROM duty_dutyassignment a JOIN duty_period p ON p.id = a.period_id WHERE p.board_id = b.id AND a.cell LIKE 'slot%') FROM duty_board b WHERE b.input_mode = 'direct';"`
  - 되돌리기는 기본이 위 "롤백"(코드 되돌리기 + 업그레이드 전 백업 `restore`)이다. `migrate` 거꾸로를 쓰려면 롤백 순서대로 `sudo systemctl stop duty-web duty-worker` 와 `backup` 을 한 뒤, **코드를 되돌리기 전에**(새 코드 그대로) `sudo -u duty .venv/bin/python manage.py migrate duty 0022` 를 하고, 그다음 `sudo git checkout <적어 둔 버전>` 부터 이어 간다(이때 `restore` 는 하지 않는다). 옛 코드에는 0023 파일이 없어 코드를 먼저 되돌리면 거꾸로 돌지 않는다. 0023 은 입력 방식으로 나타낼 수 없는 근무표(단계 하나만 끔, 이름을 고침)가 있으면 그 코드를 알려 주며 거꾸로 돌기를 거부한다. 헷갈리면 `restore` 만 쓴다.
- **근무표 통합 2단계로 올릴 때**: 마이그레이션이 없다(`migrate` 는 "No migrations to apply"). **IT 근무표에 취합 중·마감·생성됨 회차가 하나도 없을 때(작성 중·배포됨만, 보통 배포 직후 ~ 다음 [취합 열기] 전) 올린다**. 아래가 아무것도 안 나오면 올려도 된다.
    `sudo -u duty sqlite3 -readonly data/db.sqlite3 "SELECT p.id, p.status FROM duty_period p JOIN duty_board b ON b.id = p.board_id WHERE b.code = 'it' AND p.status IN ('collecting', 'closed', 'generated');"`
  - **올리기 직전에 확인 ②를 다시 돌린다**(1단계 전에 적어 둔 값이 아니라 지금 값으로 공지와 진행을 정한다). 작성 중·마감을 둘 다 끈 근무표마다 `코드|켜진 관제 정의 수|관제 배정 행 수`:
    `sudo -u duty sqlite3 -readonly data/db.sqlite3 "SELECT b.code, (SELECT COUNT(*) FROM duty_boardshift s WHERE s.board_id = b.id AND s.active = 1 AND s.key LIKE 'slot%'), (SELECT COUNT(*) FROM duty_dutyassignment a JOIN duty_period p ON p.id = a.period_id WHERE p.board_id = b.id AND a.cell LIKE 'slot%') FROM duty_board b WHERE b.use_draft = 0 AND b.use_close = 0;"`
    - 켜진 관제 정의가 1 이상인 근무표: 2단계부터 [확정] 대신 [장중관제 생성]이, 생성됨에서 [재생성]이, [생성 방식] 버튼·상자가 보이고 생성하면 관제를 배정한다. 그 근무표가 관제를 쓰지 않으면 올리기 전에 관리 화면 근무표에서 그 관제 줄의 "사용"을 끈다(그러면 아래 경우가 된다). 쓰면 그 근무표 관리자에게 공지한다.

- **메모 알림을 근무표 설정으로 옮길 때(0028)**: `migrate` 가 사람마다의 메모 알림 스위치(`User.notify_memos`)를 지우고 근무표마다의 `Board.notify_memos`(꺼짐)를 더한다. 그전에 켜 둔 사람의 설정은 사라지니, 메모를 공지로 쓸 근무표는 관리자가 [근무표 설정] → 알림 → '메모 알림'을 켠다. 업그레이드 절차 그대로(작업자 재시작 포함).
- **근무표 화면 개선(2026-11-23)으로 올릴 때 (한 번)**: `migrate` 가 0026(메모 알림: `User.notify_memos`, `Memo` 의 알림 대기·쓴 사람·쓴 때)과 0027(필터 흐리게: `RosterPref.dims`)을 적용한다. 칸만 더하는 변경이라 옮기는 데이터가 없고, 업그레이드 절차 그대로다. `collectstatic` 을 빠뜨리면 새 화면 스크립트(`duty/roster.js`)가 해시 목록에 없어 근무표 화면이 500 이다. 작업자도 다시 띄워야 메모 알림이 나간다(절차의 `systemctl start duty-web duty-worker` 그대로). 새 라이브러리는 없다.
  - 바뀌는 것(공지할 만한 것): 근무표 화면 모양(한 줄 도구 막대, 내 이름 빨간 이름표, 오늘 파란 테두리, 근무조 색 띠, 관제 접기, 토·일 칸), 필터 체크 상자가 누를 때마다 보임 → 흐리게 → 숨김, 월간이 일요일부터, 좌우로 밀어 넘기기, 메모 알림(근무표마다 [근무표 설정] '알림' 칸에서 관리자가 켠다, 처음에는 꺼짐), 푸시 알림 글이 텔레그램과 같아짐(0028 에서 바뀜). 저장돼 있던 필터·보기 설정은 그대로 이어진다. 도움말 글·영상도 새 화면으로 바뀌었다.
  - 올리기 전부터 열어 둔 화면은 새로고침해야 새 모양이 된다(정적 파일은 해시 이름이라 브라우저 캐시를 지울 필요는 없다).
  - 되돌리기는 위 "롤백"(코드 되돌리기 + 업그레이드 전 백업 `restore`)이 기본이다. 거꾸로(`migrate duty 0025`)도 되지만 그사이 저장한 메모 알림 설정·흐리게 값이 지워진다.
- **계정·세션 보안 손질(2026-11-24)로 올릴 때**: `migrate` 가 0029(`User.temp_password_issued_at`)를 적용하고, 지금 첫 로그인 대기인 사람은 업그레이드한 때 발급한 것으로 친다(그때부터 7일 안에 첫 로그인해야 한다). 업그레이드 절차 그대로(`collectstatic`·nginx·systemd·`.env` 변화 없음). 로그인해 있는 사람을 쫓아내지 않는다: 이미 로그인한 슈퍼유저 세션은 원래 기한(90일)대로 남으니 업그레이드 뒤 슈퍼유저는 한 번 로그아웃했다 다시 들어온다(그때부터 12시간). 이미 쌓인 로그인 성공 기록은 `sudo -u duty .venv/bin/python manage.py axes_reset_logs --age 0` 으로 지운다(실패 기록·잠금은 그대로). 되돌리기는 코드만 되돌려도 된다(칸 하나가 남을 뿐).
- nginx 를 켜 둔 서버는 이 묶음을 마친 뒤 아래 "nginx → 평소 운영"의 **업그레이드 뒤 nginx 설정 갱신**을 한다(대부분 "같음"으로 끝난다).
- git 이 "dubious ownership" 을 내면 앞에 `sudo` 를 빠뜨린 것이다(코드 폴더는 root 소유). `sudo` 를 붙여 다시 한다. 그래도 나오면 `sudo chown -R root:root /opt/duty_generator/.git` 후 다시 한다.
- 업그레이드 전 백업도 `db-*` 라 `DUTY_BACKUP_KEEP_DAYS` 일 뒤 자동으로 지워진다. 오래 둘 것은 서버 밖으로 내려받는다.

## 백업·복원

- 자동: 작업자가 매일 `DUTY_BACKUP_HOUR` 시(기본 3시) 이후 처음 돌 때 `data/backups/db-YYYYMMDD.sqlite3` 를 만들고, `DUTY_BACKUP_KEEP_DAYS` 일(기본 30)보다 오래된 `db-*` 를 지운다. 작업자가 꺼져 있었으면 다시 켜질 때 그날 것을 만든다(26시간 안 백업이 없으면 그 시각 전이라도 바로).
- 서버 밖 사본(권장): `.env` 의 `DUTY_BACKUP_COPY_DIR` 에 다른 디스크·NAS 가 마운트된 폴더를 적으면, 하루 백업을 만든 뒤 같은 파일을 그 폴더에도 한 벌 두고 같은 보관 일수로 정리한다(수동 `backup`·업그레이드 전 백업은 복사하지 않는다). 폴더는 미리 만들고 `duty` 사용자가 쓸 수 있게 한다(`sudo install -d -o duty -g duty -m 700 /mnt/nas/duty-backups`). 폴더가 없으면 만들지 않고 실패해 `worker.log` 에 `worker job failed: backup` 이 남는다(마운트가 빠진 채 로컬 디스크의 빈 마운트 지점에 쓰지 않게). 그날은 다시 하지 않으며, 26시간 동안 사본이 없으면 장애 알림 "백업 사본(DUTY_BACKUP_COPY_DIR)에 26시간 안에 만든 백업 없음"이 온다. 마운트한 뒤 바로 한 벌 두려면 `sudo -u duty cp -p data/backups/db-<오늘>.sqlite3 <사본 폴더>/` 한다(이미 만든 백업 파일이라 `cp` 로 괜찮다). 값을 바꾸면 `sudo systemctl restart duty-worker`.
  - 작업자 유닛의 샌드박스(`ProtectSystem=strict`)가 `data/` 밖 쓰기를 막으므로, 켤 때 꼭 `sudo systemctl edit duty-worker` 로 `[Service]` 아래 `ReadWritePaths=-<사본 폴더>` 한 줄을 더하고 `sudo systemctl restart duty-worker` 한다(빠뜨리면 "Read-only file system"으로 실패한다. 저장소의 유닛 파일은 고치지 않는다). 앞의 `-` 를 꼭 붙인다: 없으면 부팅 때 NAS 가 아직 안 붙어 폴더가 없을 때 작업자가 아예 뜨지 않는다(알림까지 멈춤). `-` 가 있으면 작업자는 뜨고 그날 사본만 실패하므로, 마운트한 뒤 `sudo systemctl restart duty-worker` 한다. `ProtectHome=yes` 라 `/home` 아래 폴더는 쓰지 않는다.
- 수동: `sudo -u duty .venv/bin/python manage.py backup` → `data/backups/db-YYYYMMDD-HHMMSS.sqlite3`. 서비스가 도는 중에도 된다. **DB 파일을 `cp` 로 복사하지 말 것**(WAL 모드라 최근 변경이 빠지거나 깨진 사본이 될 수 있다). 백업은 SQLite 백업 기능으로 떠서 일관된 파일 하나가 된다.
- 백업에는 실명, 비밀번호 해시, 텔레그램 봇 토큰·푸시 키가 들어 있다(로그인 세션은 백업에서 지우고, 파일 권한은 600). 복원하면 모두 다시 로그인한다. 서버 밖에 보관하려면 내려받되 공유 폴더에 두지 않는다.
- 복원:
  ```bash
  sudo systemctl stop duty-web duty-worker
  sudo -u duty .venv/bin/python manage.py restore data/backups/<백업 파일>
  sudo -u duty .venv/bin/python manage.py migrate
  sudo systemctl start duty-web duty-worker
  ```
  - 작업자가 돌고 있으면(`data/.alarms.lock` 이 잡혀 있으면) 아무것도 바꾸지 않고 멈춘다. 복원하는 동안은 이 잠금을 잡고 있어 작업자가 뜨지 못한다. 웹은 검사하지 않으니 직접 멈춘다.
  - 복원 전에 검사한다. `quick_check` 가 `ok` 가 아니거나 백업의 마이그레이션이 지금 코드와 다르면 아무것도 바꾸지 않고 멈춘다(다르면 그 백업을 만든 버전의 코드로 먼저 바꾼다).
  - 지금 DB 는 `data/backups/before-restore-YYYYMMDD-HHMMSS.sqlite3` 로 남긴다(자동으로 지우지 않는다). 남은 `-wal`·`-shm` 은 지운다.

## 서버에서 데이터 보기

`duty` 는 로그인할 수 없는 계정이라(`/sbin/nologin`) `su - duty` 로는 안 들어가진다. 계정을 바꾸지 않고 `sudo` 로 본다.

```bash
cd /opt/duty_generator
sudo ls -la data data/backups data/logs
sudo tail -f data/logs/worker.log         # 작업자 로그 (web.log 는 웹)
sudo -u duty bash                         # duty 로 셸이 꼭 필요할 때. 나갈 때 exit
```

DB 안을 볼 때는 읽기 전용으로 연다(서비스가 도는 중에도 안전).

```bash
sudo dnf install -y sqlite                # 처음 한 번
sudo -u duty sqlite3 -readonly data/db.sqlite3
# sqlite> .tables
# sqlite> select id, name, status from duty_period;
# sqlite> .quit
```

브라우저로 보고 싶으면 [sqlite-web](https://github.com/coleifer/sqlite-web) 을 **앱과 따로** 설치해 읽기 전용으로 띄운다(앱 의존성에 넣지 않는다).

```bash
sudo python3.12 -m venv /opt/sqlite-web && sudo /opt/sqlite-web/bin/pip install sqlite-web==0.8.2   # 처음 한 번(버전 고정)
sudo -u duty /opt/sqlite-web/bin/sqlite_web -r -P -x -H 127.0.0.1 -p 8092 /opt/duty_generator/data/db.sqlite3
# 다 보면 Ctrl+C 로 끈다(켜 둔 채로 두지 않는다)
```

- `-r` 읽기 전용, `-P` 띄울 때 정한 비밀번호를 물어봄(서버의 다른 사용자가 같은 포트로 들어오지 못하게), `-x` 브라우저 자동 실행 안 함, `-H 127.0.0.1` 서버 안에서만 열기.
- 단순 조회는 위의 `sqlite3 -readonly` 가 더 안전하다. sqlite-web 은 화면이 필요할 때만 잠깐 띄운다.
- 내 PC 에서는 SSH 터널로 본다: `ssh -L 8092:127.0.0.1:8092 <서버>` 후 브라우저에서 `http://127.0.0.1:8092`. VS Code 원격 접속 중이면 포트 전달이 자동으로 잡힌다.
- **Tailscale Funnel 에 올리지 않는다**(실명·봇 토큰이 그대로 보인다). `-H 0.0.0.0` 으로 열지 않는다.
- `-r` 없이 띄우면 행 추가·수정·삭제와 SQL 실행도 된다. **쓰기는 웬만하면 하지 않는다**: 변경 기록(ChangeLog)·지난 날짜 권한 같은 앱 규칙을 건너뛰고, sqlite-web 은 외래키 검사를 켜지 않아 기록이 남은 사람·회차를 지워도 막히지 않으며, 서비스가 도는 중이면 잠금이 겹친다. 꼭 고쳐야 하면 이 순서로만 한다.
  ```bash
  sudo systemctl stop duty-web duty-worker
  sudo -u duty .venv/bin/python manage.py backup        # 잘못되면 이 파일로 restore
  sudo -u duty /opt/sqlite-web/bin/sqlite_web -P -x -H 127.0.0.1 -p 8092 /opt/duty_generator/data/db.sqlite3   # -r 없음
  # 고친 뒤 Ctrl+C
  sudo systemctl start duty-web duty-worker
  ```
  자주 직접 고치게 되는 것이 있으면 화면 기능으로 넣는다.

- 데이터는 DB 를 직접 고치지 말고 웹 화면·관리 화면에서 고친다(직접 고치면 변경 기록이 남지 않고 규칙 검사도 건너뛴다).
- DB 에는 실명과 봇 토큰이 들어 있다. 화면을 캡처하거나 결과를 밖으로 옮기지 않는다.

## 로그

| 파일 | 내용 |
|---|---|
| `data/logs/web.log` | 웹 앱의 경고·오류(`django.request` 404·500 등, 로그인 잠금) |
| `/var/log/nginx/duty-error.log` | nginx: gunicorn 에 못 붙음(502) 등. 정리는 nginx 패키지의 logrotate 가 한다 |
| `data/logs/worker.log` | 작업자: 매분 `alarms tick:` 한 줄, 발송 실패, `backup: db-…`, `health: …`, `worker job failed: …` |

- 자정마다 새 파일로 넘기고(`web.log.2026-11-10` …) `DUTY_LOG_KEEP_DAYS` 일(기본 14)보다 오래된 파일은 지운다.
- 같은 내용과 gunicorn 자체 메시지는 journald 에도 간다: `journalctl -u duty-web -n 100`, `journalctl -u duty-worker -f`.
- 읽기: `sudo tail -f /opt/duty_generator/data/logs/worker.log`. 경고·오류만: `sudo grep -E ' (WARNING|ERROR) ' /opt/duty_generator/data/logs/*.log`.
- 각 줄은 `<날짜 시각> <레벨> <로거> <메시지>` 형식이다.
- 접근 로그(요청마다 한 줄)는 남기지 않는다. 캘린더 구독 주소에 비밀 토큰이 들어 있어서다.

## 장애 알림

작업자가 5분마다 아래를 보고, **상태가 바뀔 때만** 관리자 텔레그램으로 알린다(문제가 생겼을 때 한 번, 정상으로 돌아왔을 때 한 번).

- 웹이 응답하지 않음: nginx 를 거친 `http://127.0.0.1:8008/login/` 이 실패하면 웹(`127.0.0.1:8090`)을 한 번 더 보고 "nginx 응답 없음(웹은 정상)" 또는 "웹 응답 없음"으로 나눠 알린다 / 26시간 안에 만든 `db-*` 백업이 없음(`DUTY_BACKUP_COPY_DIR` 를 정했으면 그 사본 폴더도 따로 본다) / `data/` 디스크 사용 90% 이상
- 보내는 봇은 알림용 텔레그램 봇, 받는 곳은 관리 화면 → 알림 설정의 "장애 알림 받을 chat_id"다. 비우면 `worker.log` 에만 남는다.
  - **단톡방**(추천): 알림 봇을 방에 초대한 뒤, PC 브라우저로 `https://web.telegram.org/a/` 에서 그 방을 열면 주소창 끝 `#-100…` 숫자가 chat_id 다(음수). 다른 봇을 방에 넣어 알아내지 않는다(대화가 바깥 봇에 보인다).
  - **개인**: 텔레그램에서 `@userinfobot` 에게 아무 말이나 보내면 알려 준다(양수).
- 작업자가 켜진 직후 첫 바퀴는 점검을 건너뛴다(재부팅·업그레이드 때 아직 뜨는 중인 웹을 "응답 없음"으로 알리지 않게). 첫 점검은 켜지고 5분 뒤, 그 뒤로는 마지막 점검에서 5분이 지난 첫 바퀴다(알림 발송이 오래 걸려 한 바퀴가 1분을 넘겨도 점검을 건너뛰지 않는다).
- 첫 점검이 정상이면 `health: 정상(점검 시작)` 한 줄만 남기고 알리지 않는다. 마지막 상태는 `data/.health.state` 에 있다.
- 발송에 실패하면 상태를 저장하지 않아 다음 점검(5분 뒤)에 다시 보낸다.
- 웹 점검이 `127.0.0.1` 로 부르므로 `DUTY_ALLOWED_HOSTS` 에 `127.0.0.1` 이 있어야 한다.
- 작업자 자체가 멈추면 이 알림도 멈춘다. 대신 작업자가 바퀴마다 `data/.worker.alive` 의 시각을 고치고, 그 시각이 10분보다 오래되면 웹이 **슈퍼유저 화면 맨 위**에 빨간 경고 "작업자(run_worker)가 10분 넘게 돌지 않습니다"를 띄운다(텔레그램은 오지 않는다. 작업자가 보내는 것이라서). 파일이 아예 없으면(작업자를 한 번도 안 돌린 개발 PC) 띄우지 않는다. 경고가 보이면 `systemctl status duty-worker` 와 `worker.log` 의 매분 `alarms tick:` 줄로 확인한다.
- 시험: `sudo systemctl stop duty-web` → 5분 안에 "웹 응답 없음" 알림 → `sudo systemctl start duty-web` → 복구 알림. nginx 만 멈추면(`sudo systemctl stop nginx`) "nginx 응답 없음(웹은 정상)"이 온다(이때 바깥 사용자는 접속이 안 된다).

## 개발 PC DB 를 서버로 옮기기 (처음 한 번)

서버는 개발 PC 에서 쓰던 DB 를 그대로 가져가 시작한다. 계정·비밀번호·근무·기록·알림 설정(봇 토큰·푸시 키)이 전부 같이 간다.

```bash
# 개발 PC (저장소 루트): runserver·run_worker 를 멈추고, 서버에 올릴 것과 같은 코드(main)에서
git pull --ff-only
DUTY_DEBUG=1 .venv/bin/python manage.py migrate   # 서버 코드와 마이그레이션을 맞춘다(안 맞으면 restore 가 거부한다)
DUTY_DEBUG=1 .venv/bin/python manage.py backup   # data/backups/db-YYYYMMDD-HHMMSS.sqlite3 (경로가 출력된다)
scp data/backups/db-<시각>.sqlite3 <서버>:duty.sqlite3   # 서버의 내 홈 폴더로(/tmp 는 다른 사용자도 본다)

# 서버: "설치"를 migrate 직전까지 한 뒤 (createsuperuser 는 하지 않는다 — 계정은 DB 에 있다)
sudo systemctl stop duty-web duty-worker 2>/dev/null
sudo install -o duty -g duty -m 600 ~/duty.sqlite3 data/import.sqlite3 && rm ~/duty.sqlite3
sudo -u duty .venv/bin/python manage.py restore data/import.sqlite3 && sudo rm data/import.sqlite3
sudo -u duty .venv/bin/python manage.py migrate
# 이어서 "설치"의 check --deploy 부터
```

- **DB 파일을 `cp` 로 복사하지 말고 `backup` 으로 뜬다**(WAL 모드라 그냥 복사하면 최근 변경이 빠질 수 있다).
- `restore` 는 파일의 마이그레이션이 서버 코드와 같아야 받는다. 개발 PC 와 서버를 같은 커밋으로 맞춘다.
- 옮긴 뒤에는 **개발 PC 에서 그 DB 로 `run_worker` 를 켜지 않는다**. 같은 봇 토큰으로 두 곳이 알림을 보내고 텔레그램 연결 확인이 서로 엉킨다. 개발 PC 에서 알림을 시험하려면 관리 화면 → 알림 설정에서 토큰을 지우거나 다른 시험용 봇을 넣는다.
- 웹 푸시는 주소(127.0.0.1 → 서버 도메인)가 바뀌어서 개발 PC 에서 등록한 기기는 서버에서 받지 못한다. 각자 서버 주소로 들어가 [이 기기에서 푸시 받기]를 다시 누른다. 텔레그램 연결은 그대로 쓰인다. 캘린더 구독은 주소가 바뀌므로 알림·캘린더 화면에서 다시 발급받는다.
- 개발 PC 에 남은 DB 와 백업에는 실명과 봇 토큰이 들어 있다. 공유 폴더에 두지 않는다.

## 알림 (텔레그램·웹 푸시)

사용자가 `/alarms/` 에서 규칙을 만들면 작업자(`run_worker`, 1분마다)가 보낸다. 웹과 별도 프로세스다.

### 설정: 관리 화면 → 알림 설정

봇 토큰·푸시 키는 `.env` 가 아니라 DB 에 한 행으로 두고, 슈퍼유저가 `/<DUTY_ADMIN_PATH>/` → "알림 설정"에서 고친다. 저장하면 웹·작업자가 바로 새 값을 쓴다(재시작 불필요).

| 칸 | 내용 |
|---|---|
| 텔레그램 봇 토큰 | 웹앱 전용 봇 토큰. 비우면 텔레그램 채널이 꺼진다. 화면에는 끝 4자리만 보인다. **칸을 비워 두고 저장하면 지금 값 그대로**, 새 값을 넣으면 교체, "토큰 지우기"를 체크하면 비운다. |
| 텔레그램 봇 사용자명 | 그 봇의 사용자명(`@` 는 떼고 저장). **꼭 넣는다**: 사용자는 [텔레그램 연결](봇에게 `/start <일회용 코드>`)로만 연결하므로, 비우면 아무도 연결할 수 없다. |
| 장애 알림 받을 chat_id | 단톡방(음수, `-100…`) 또는 개인(양수). 위 "장애 알림" 참고. |
| 웹 푸시 연락처 | **실제 메일 주소**(`mailto:it@회사도메인`) 또는 사이트 주소(`https://…ts.net`). 기본값 `mailto:admin@localhost` 는 애플(아이폰) 푸시가 거절해 아이폰만 테스트 푸시가 실패한다. 바꿔도 기기를 다시 등록할 필요는 없다. |
| 푸시 키 | 처음 필요할 때(누군가 `/alarms/` 를 열 때) 자동으로 만든다. 손으로 만들 필요 없다. |
| 푸시 키 다시 만들기 | 키가 유출됐을 때만. 체크하고 저장하면 모든 기기의 푸시 구독이 지워지고, 사용자마다 [이 기기에서 푸시 받기]를 다시 눌러야 한다. |

- **봇을 바꾸면**(토큰이나 사용자명 변경) 모든 사용자의 텔레그램 연결 확인이 지워진다. 새 봇에서 [시작]을 다시 눌러야 하기 때문이다. 저장 뒤 화면에 몇 명인지 나온다. 각자 `/alarms/` 에서 [텔레그램 연결] → [시작] → [연결 확인]을 다시 하면 된다.
- 토큰·개인키는 로그와 화면에 나오지 않는다. DB 백업에는 들어 있으니 백업 파일도 비밀로 다룬다.

`.env` 에 남는 알림 관련 값은 하나다:

| 변수 | 내용 |
|---|---|
| `DUTY_SITE_URL` | `https://duty.example.ts.net`(경로 없이 호스트만). 텔레그램 알림 링크·캘린더 구독 주소용(비면 링크 생략, 캘린더 구독 주소 발급 불가). |

### 텔레그램 봇

봇은 이 웹앱만 써야 한다. 다른 프로그램(개발 PC 의 `run_worker` 포함)이 같은 봇으로 polling 중이면 서로의 업데이트를 가로챈다(409 충돌).

1. 텔레그램 `@BotFather` 에서 `/newbot` → 토큰과 사용자명을 관리 화면 → 알림 설정에 넣는다.
2. 사용자는 `/alarms/` 의 [텔레그램 연결] → 봇에서 [시작] → [연결 확인]으로 직접 연결한다. 서버에서 따로 할 일은 없다.

[연결 확인]이 "텔레그램 봇 설정 오류입니다."를 띄우면 `getUpdates` 가 4xx 로 거절된 것이다. 대개 409(그 봇에 webhook 이 걸렸거나 다른 프로그램이 같은 봇으로 polling 중) 또는 401(토큰 오류)이다. 토큰을 다시 확인하고, 다른 프로그램이 같은 봇을 쓰고 있지 않은지 본다. 원인을 못 찾으면 BotFather 에서 새 봇을 만들어 알림 설정의 토큰·사용자명을 바꾸는 것이 가장 빠르다(사용자는 다시 연결해야 한다).

### 웹 푸시 지원 범위

- 받는 쪽 푸시 서비스는 Chrome·Android(FCM), Firefox(Mozilla), Safari·iOS(Apple)만 허용한다. Edge(WNS)는 지원하지 않는다(구독 시 "지원하지 않는 푸시 서비스입니다.").
- 한 사용자당 기기 20대까지.
- 아이폰·아이패드: iOS 16.4 이상에서 Safari 로 사이트를 연 뒤 공유 → "홈 화면에 추가" 한 앱에서만 푸시를 받을 수 있다. 그 홈 화면 앱 안에서 `/alarms/` → [이 기기에서 푸시 받기]를 누른다. 사파리 탭에서는 안 된다. 안내 화면: `/help/push/`.

### 로그 읽기 (`data/logs/worker.log`)

- 각 줄은 `<날짜 시각> <레벨> <로거> <메시지>` 형식이다(예: `2026-11-11 09:00:00 INFO duty.services.alarm_runner alarms tick: ...`, 실패는 `WARNING`). 실패만 보려면 `sudo grep -E ' (WARNING|ERROR) ' /opt/duty_generator/data/logs/worker.log`.
- 매분 `alarms tick: due=<보낼 건수> sent=<성공> failed=<실패>`.
- 실패마다 `alarm send failed rule=<규칙 id> channel=<telegram|push> delivery=<기록 id> status=<종류>:<HTTP 코드> attempt=<시도 횟수>`. `status` 는 결과 상태가 아니라 실패 종류와 응답 코드를 붙인 것이다(코드가 없으면 `None`).
  - `Temporary:None` — 네트워크 오류·응답 이상·깨진 VAPID 키. 1, 2, 4 … 최대 30분 간격으로 재시도.
  - `Temporary:<5xx>` — 상대 서버 오류. 위와 같이 재시도(텔레그램 503 도 여기).
  - 푸시만 `Temporary:401`/`403` — 푸시 키·연락처(subject) 설정 오류일 가능성. 재시도하므로 관리 화면 → 알림 설정에서 연락처를 고치면 다시 나간다.
  - `RetryLater:429`(텔레그램·푸시), `RetryLater:503`(푸시만) — 상대가 알려 준 시간(`retry_after`/`Retry-After`) 뒤 재시도. 시간을 안 알려 주면 위의 일반 간격.
  - `Permanent:<4xx>` — 그 알림은 만료 시각까지 다시 보내지 않는다. 텔레그램 `Permanent:401` 은 봇 토큰 오류, `Permanent:403` 은 사용자가 봇을 차단, `Permanent:400` 은 chat_id 오류. 푸시는 401·403·404·410·429 를 뺀 4xx(구독 데이터 이상 등).
  - 그 밖의 이름(예: `OperationalError:None`)은 예기치 않은 예외 — 일시 실패로 재시도된다. 계속 나오면 확인한다.
- 만료된 푸시 구독(404/410)은 로그 없이 지워진다. 기기에서 다시 [이 기기에서 푸시 받기]를 누르면 된다.

### 알림 켜기

작업자는 늘 돈다(백업·상태 점검). 알림은 보낼 곳이 생기면 그때부터 나간다: 텔레그램은 관리 화면에 봇 토큰이 있고 사용자가 연결했을 때, 푸시는 사용자가 기기를 등록했을 때.

1. 관리 화면 → 알림 설정에 봇 토큰·사용자명을 넣는다(위 "텔레그램 봇").
2. `sudo -u duty .venv/bin/python manage.py run_worker --dry-run` — 발송·기록 없이 `telegram=<n> push=<n>`(지금 보낼 건수)만 출력한다. 작업자가 도는 중에도 된다.
3. `/alarms/` 에서 텔레그램 연결 또는 chat_id [저장 및 테스트], 푸시 [이 기기에서 푸시 받기] → [테스트 푸시]로 실제 수신을 확인한다. PC Chrome 과 아이폰 홈 화면 앱에서 알림을 누르면 해당 화면이 열리는지도 본다.
4. `sudo tail -f /opt/duty_generator/data/logs/worker.log` 에서 매분 `alarms tick:` 줄이 찍히는지 확인한다.
5. 텔레그램 알림을 모두 멈추려면 관리 화면 → 알림 설정에서 "토큰 지우기". (푸시만 따로 끄는 스위치는 없다. 사용자가 기기를 해제하거나 규칙을 끈다.)

## 휴장일

- 관리 화면 "휴장일"(슈퍼유저): 모든 근무표 공통. 작업자가 매 바퀴 공휴일 라이브러리로 올해·내년(회차가 있는 해까지)의 공휴일과 12/31 "연말 휴장"을 채운다(출처 "자동"). 이미 있는 날짜는 건드리지 않는다.
- 임시공휴일: [휴장일 추가]로 날짜·이름을 넣는다(출처 "직접 추가"). 휴장일이 아닌 날은 목록에서 "휴장"을 끄고 저장한다. 지우기는 없다(지운 자동 휴장일이 다음 바퀴에 다시 생기므로 끈다). 날짜를 잘못 넣었으면 그 행을 끄고 새로 추가한다.
- 바꾼 휴장일은 2단계 업그레이드 뒤에 만든 회차(`skip_holidays` 켜짐)에만 반영된다: 배포 전 회차의 입력 표(다음에 열 때)와 생성(돌릴 때). 업그레이드 전에 만든 회차는 휴장일도 평일처럼 입력·생성한다(이 값은 화면에서 바꿀 수 없다). 그런 회차에서 휴장일을 비우려면 근무표 관리자가 그날 [메모]에서 "근무 없음"으로 적는다(입력 표가 그날을 잠그고 생성이 건너뛴다). 그냥 두면 그날도 근무가 있는 날로 남는다. 이미 배정된 근무는 지우지 않는다: 휴장일에 사람이 들어 있으면 근무 변경 "빼기만"으로 뺀다. 이미 배포된 빈 휴장일을 끄면 그날은 빈 날이라 "넣기"로 채운다.
- 영업일 기준 알림은 켜진 휴장일을 영업일에서 뺀다. 휴장일을 바꿔 발송일이 달라져도 이미 보낸 알림은 다시 보내지 않는다.
- 근무표 하나만 쉬는 날은 휴장일이 아니라 그 근무표 관리자가 날짜 칸의 [메모]에서 "근무 없음"으로 적는다(그날 근무가 있으면 확인 뒤 지우고 기록이 남는다).
- 라이브러리가 모르는 새 공휴일은 위처럼 직접 추가하고, 업그레이드 때 `requirements.lock` 의 `holidays` 버전을 올린다(DEVELOPMENT.md "의존성 고정"). 버전은 lock 에 고정돼 있고(지금 0.108), 올리면 자동으로 채워지는 휴장일이 달라질 수 있다(이미 있는 행은 그대로, 표에 없는 날짜만 새로 들어간다). `tests/test_holidays.py` 의 기대값이 0.108 데이터 기준이라 올릴 때 같이 확인한다.

## 캘린더 구독 (ICS)

- 각자 [알림·캘린더] 화면에서 [구독 주소 만들기]로 개인 구독 주소(`/calendar/<토큰>.ics`)를 받아 Google 캘린더·아이폰·Outlook에 구독한다. 사용 방법은 `/help/calendar/`.
- 피드에는 배포된 회차의 본인 출근조·관제·점심당번(부서 점심 시각이 있을 때) 일정만, 오늘 기준 지난 90일부터 나온다. 사유(휴가 등)가 붙은 날은 그 사람의 그날 일정(관제·점심당번 포함)이 모두 빠진다. 퇴사(재직 끔)면 빈 캘린더가 된다. 부서 없는 계정은 구독 주소를 만들 수 없다.
- 갱신 시점은 캘린더 앱이 정한다(Google은 몇 시간 이상 걸리기도 함). 즉시 알아야 하는 변경은 텔레그램·푸시 알림이 맡는다.
- DB에는 토큰의 SHA-256 해시만 남고 주소는 발급 화면에 한 번만 보인다. 주소가 유출되면 본인이 [주소 재발급](기존 주소 즉시 무효) 또는 [구독 끄기]를 누른다. 피드 경로는 앱 로그(`django.request`·`django.server`)에서 `calendar feed <상태코드>`로 바뀌어 남는다.
- `DUTY_SITE_URL`이 비어 있으면 주소를 발급할 수 없다. 값은 경로 없이 `https://호스트[:포트]` 형식만 허용(DEBUG에서만 `http`), 경로·공백·제어문자·`?`·`#`·`user@`·잘못된 포트가 있으면 서버가 시작하지 않는다.
- 피드 오류 로그에 지역 변수를 담는 도구(HTML 오류 메일 `include_html`, 지역 변수 수집 APM)를 켜지 말 것 — 토큰이 포함될 수 있음.

## 운영 메모

- 로그인을 같은 곳(접속 IP)에서 5회 틀리면 그 아이디는 **그 IP 에서만** 15분 잠긴다(다른 곳에서는 그대로 로그인된다). 슈퍼유저가 Admin의 Axes 메뉴에서 해제할 수 있다.
  IP 는 Tailscale Funnel 이 실제 접속 IP 하나로 덮어써 넘기고(클라이언트가 적어 보낸 값은 버린다) nginx 가 그 값을 웹에 넘긴 것이다(`duty/client_ip.py`, 127.0.0.1 에서 온 요청만 믿는다). 그래서 아이디만 아는 남이 그 계정을 잠그지 못한다. IPv6 는 /64 네트워크 하나를 한 IP 로 친다(그 안의 주소를 돌려 써도 같이 센다. 잠금 해제·`axes_reset_ip` 에도 /64 의 첫 주소, 예: `2001:db8:1:2::`). 한계: 여러 IP(IPv4 여러 개, IPv6 /64 여러 개)를 돌려 쓰면 IP 마다 5번씩 시도할 수 있다(비밀번호 규칙이 막는다). 로그인 성공 기록(Axes 관리 화면의 "접근 로그")은 남기지 않는다. 잠긴 동안의 시도는 잠금을 늘리지 않는다. 슈퍼유저가 Axes 관리 화면에서 풀거나, 서버에서 바로 푼다:
  ```bash
  sudo -u duty .venv/bin/python manage.py axes_reset_username <아이디>
  ```
  어드민 계정이 잠겨 관리 화면에 못 들어갈 때도 이 명령으로 푼다.
- 근무 정의 편집(관리 화면 "근무표"): 저장한 정의 둘의 이름을 한 저장에서 함께 바꾸다 새 이름이 다른 정의의 지금 이름과 같아지면(맞바꾸기 등) Django 기본 겹침 문구로 막힌다. 한 번에 하나씩(필요하면 임시 이름을 거쳐) 바꾼다.
- 퇴사자는 근무표 관리자가 [근무표 설정] → 사람에서 [퇴사]한다(관리자 계정은 슈퍼유저가 사용자 "재직"을 끄고 위 표 "관리자 퇴사"대로 액션으로 연결도 끊는다. 관리 화면에서 재직만 끄면 비밀번호와 텔레그램·푸시 연결 행은 남는다. 캘린더 피드는 재직 검사로 막힌다. 이런 사람도 [다시 재직]하면 옛 비밀번호와 연결이 모두 끊기고 '발급 전'이 된다). 근무표 후보에서 빠지고 로그인도 막힌다(어드민도 예외 없음). 지난 근무·기록·통계에는 그대로 남는다.
