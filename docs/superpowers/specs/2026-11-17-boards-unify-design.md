# 근무표 통합(입력 방식 갈래 제거·근무표 설정 화면·여러 근무표 한 화면) 설계

- 상태: 사용자 검토 대기(Codex 리뷰 전 초안)
- 목표: IT 당번표와 시장운영실을 **같은 코드 한 길**로 돌린다. 근무표마다 다른 점은 코드 갈래(`Board.input_mode`)가 아니라 **근무표 설정 값(데이터)**으로 둔다. 근무표 관리자가 슈퍼유저·관리 화면을 거치지 않고 앱 안의 [근무표 설정] 한 화면에서 운영한다. 근무표 화면은 근무표 N개를 한 번에 볼 수 있게 한다.
- 출발점: `main` 02c79c5(PR #41). **운영 서버가 이 버전으로 돌고 있다**(근무표 일반화 1~4단계 + `add_board` 배포·마이그레이션 완료). 시장운영실 근무표(`input_mode=direct`)가 이미 만들어져 실제로 쓰이고 있을 수 있다. 업그레이드 설계(10절)는 이 상태의 실데이터를 전제로 한다.
- 구현이 끝나면 이 문서의 내용은 `docs/ARCHITECTURE.md`·`OVERVIEW.md`·`OPERATIONS.md`·`PRINCIPLES.md`에 합치고 이 파일은 지운다.

## 1. 배경

- 사용자 지적(2026-11-17): "IT/시장운영 두 부서의 기능들을 각각 따로 가져가는 게 아니라 한 번에 품을 수 있게 일반화해야 유지보수도 편하고 다른 부서가 추가됐을 때 좋다. 전반적으로 아예 따로 구현된 느낌이 있다", "관리자의 운영 공수가 너무 들면 안 된다".
- 지금 `Board.input_mode`(collect | direct)가 12개 파일 51곳에서 동작을 가른다(`git grep -n -E "InputMode|input_mode|\bdirect\b" -- duty`, 마이그레이션·영상 파일 포함). 갈래마다 테스트·문구·도움말이 따로 있다(`test_direct_periods.py`, `test_views_direct.py`, `help.STEPS["direct"]`).
- 운영 작업이 네 곳(Django 관리 화면·앱 화면·`add_board` 명령·[그룹] 메뉴)에, 권한 개념이 넷(슈퍼유저, 근무표 관리 그룹, 부서 입력 그룹, 그룹 관리자 `GroupKeeper`)으로 흩어져 있다. 근무표 관리자가 사람 하나를 더하려면 슈퍼유저에게 부탁해야 한다.
- 근무표 화면은 근무표 하나씩만 본다(`.seg` 버튼). 근무표가 늘수록 버튼이 늘고, 두 근무표를 같이 보는 방법이 없다.
- 보는 사람은 60세 가까운 부장들이다(변화를 싫어함, 시력이 좋지 않음). 관리자 1~2명이 다른 업무와 함께 돌린다.

## 2. 목표와 범위 밖

목표

1. `input_mode`와 그 갈래를 없앤다. 회차 단계·누가 입력하는지·채우기 버튼·빈 평일 처리가 모두 데이터와 한 규칙으로 정해진다.
2. 근무표 관리자가 [근무표 설정] 한 화면에서 관리자·사람(계정 발급 포함)·근무 정의·부서 입력 담당자·단계를 고친다.
3. 권한을 셋(근무표 관리자, 부서 입력 담당자, 슈퍼유저)으로 줄인다. 그룹 관리자와 [그룹] 화면을 없앤다.
4. 근무표 화면에서 여러 근무표를 골라 한 표에 겹쳐 본다.
5. **업그레이드한 날 IT·시장운영실 모두 보이는 동작이 그대로다**(1단계). 사용자가 정한 공통 규칙(IT 빈 평일 경고만 등)은 따로 2단계로 켠다.

범위 밖

- 근무표 만들기는 여전히 슈퍼유저(관리 화면 "근무표 추가" 또는 `manage.py add_board`). 휴장일·알림 설정·로그인 잠금 해제·부서 만들기와 부서 점심 시각·출근조도 슈퍼유저(관리 화면)에 남는다(14절 질문 1).
- 사람의 부서 옮기기·지우기(퇴사 = 재직 끄기만), 근무표 사이 사람 옮기기.
- 근무조 5개 이상(키 늘리기), 근무표 지우기, code 바꾸기.
- 사용법 영상 다시 찍기(영상은 IT 화면 그대로 맞다. 글 도움말만 고친다).

## 4. 용어

| 용어 | 뜻 |
|---|---|
| 단계 | 회차 상태(`Period.status`) 다섯 값. 근무표마다 화면 이름이 다르고, 작성 중·마감은 끌 수 있다 |
| 켠 단계 | 그 근무표가 쓰는 단계: (작성 중) → 취합 중 → (마감) → 생성됨 → 배포됨 |
| 근무표 관리자 | 그 근무표 관리 그룹(`Board.admin_group`) 멤버 |

| 고른 근무표 | 근무표 화면에서 겹쳐 볼 근무표 목록 |
| 바꿀 수 있는 근무표 | `perms.can_edit` 가 참인 근무표: 그 근무표 부서 사람(오늘 이후)이거나 그 근무표 관리자 |

## 5. 데이터 모델과 단계 규칙

정해진 값 칸은 `choices` + DB `CheckConstraint`, 기록을 남길 FK는 `PROTECT`(CLAUDE.md).

### 5.1 Board

| 칸 | 내용 |
|---|---|
| ~~input_mode~~ | 지운다(제약 `board_input_mode_valid` 와 함께) |
| use_draft | bool, 기본 참. "작성 중 단계 사용" |
| use_close | bool, 기본 참. "마감 단계 사용" |
| step_draft, step_collecting, step_closed, step_generated, step_published | 단계 화면 이름. CharField(16), 기본값 = 지금 `PeriodStatus` 이름(작성 중·취합 중·마감·생성됨·배포됨). DB 제약: 빈 글자 금지(`board_step_names_set`). 폼: 줄바꿈 금지, 다섯 이름이 서로 달라야 함 |

- 끈 단계도 이름을 가진다: 단계를 끈 뒤에도 그 상태에 남은 회차·상태 기록이 이름으로 보여야 한다(지금 `step_label` 이 직접 입력 근무표의 작성 중·마감을 `PeriodStatus` 이름으로 보이는 것과 같다).
- 단계를 켜고 끄는 것은 언제든 된다(진행 중 회차를 막지 않는다). 끈 단계에 남은 회차는 "다른 상태로 옮기기"로 켠 단계로 옮긴다(5.3 규칙이 그대로 처리한다).
- 근무 정의·부서·관리 그룹은 그대로.

### 5.2 단계 규칙(모델 메서드, 쿼리 없음)

`Board` 에 순수 메서드를 둔다(DB 를 읽지 않아 어디서 불러도 싸다). 지금 `models.step_label(board, status)`·`DIRECT_STEPS` 를 대신한다.

```python
def step_name(self, status) -> str          # 화면 이름(끈 단계도)
def steps(self) -> list[str]                # 켠 단계, 순서대로: [draft?] collecting [closed?] generated published
def first_step(self) -> str                 # draft if use_draft else collecting
def generate_from(self) -> str              # closed if use_close else collecting
def editable(self) -> set[str]              # {draft} | ({collecting} if not use_draft else set())
def move_targets(self, status) -> list[str] # [s for s in MOVABLE if s in steps() and s != status], 배포됨이면 []
```

| 규칙 | IT(둘 다 켬) | 시장운영실(둘 다 끔) | 지금 코드와 같은가 |
|---|---|---|---|
| 새 회차 상태 | 작성 중 | 취합 중(입력 중) | 같다(`save_draft` 의 `new and direct`) |
| 기간 수정 | 작성 중 | 작성 중·취합 중 | 같다(`editable`) |
| 생성(확정) 가능 | 마감·생성됨 | 취합 중·생성됨 | 같다(`run_generation` 첫 검사) |
| 옮기기 대상 | 작성 중·취합 중·마감 중 지금 것 빼고 | 취합 중만(지금이 취합 중이면 없음) | 같다(`move` 와 `_movable`) |
| 끈 단계에 남은 회차 | — | 작성 중·마감 회차 → 취합 중으로만 | 같다 |
| 출근표 입력 | 취합 중 | 취합 중 | 같다 |
| 배포 | 생성됨 | 생성됨 | 같다 |

다른 조합(작성 중만 켬, 마감만 켬)도 같은 메서드로 정해진다. 예: 마감만 끄면 작성 중 → 취합 중 → 생성됨.

### 5.3 Department

- `clean` 의 "직접 입력 근무표는 부서 하나" 검사를 지운다.
- `save` 는 근무표와 상관없이 **입력 그룹이 없으면 만든다**("<부서> 출근표 입력"). 담당자가 없는(그룹이 빈) 부서 = 관리자만 입력. 데이터 이전이 지금 그룹 없는 부서(시장운영실)에 빈 그룹을 만든다(10.1).
- 관리 화면 `DepartmentForm` 의 "직접 입력 근무표 부서는 입력 담당자 없음" 검사를 지운다.

### 5.4 버튼 이름(순수 함수)

단계 이름에서 버튼 글자를 만든다. IT·시장운영실 기본 이름에서 지금 글자가 그대로 나온다.

| 버튼 | 규칙 | IT | 시장운영실 |
|---|---|---|---|
| 취합 열기(작성 중 → 취합 중) | `step_collecting` 끝의 " 중"을 뗀 말 + " 열기" | 취합 열기 | (작성 중을 안 써서 없음) |
| 마감(취합 중 → 마감) | 같은 말 + " " + `step_closed` | 취합 마감 | (없음) |
| 생성 | 켜진 장중관제 정의가 있으면 "장중관제 생성", 없으면 `step_generated` 끝의 "됨"을 뗀 말 | 장중관제 생성 | 확정 |
| 다시 생성(생성됨) | 장중관제가 있을 때만 "재생성"(무작위라 다시 돌릴 뜻이 있다) | 재생성 | (없음) |
| 생성 취소(생성됨에서 옮길 곳이 하나뿐일 때) | 생성 버튼 말 + " 취소", 그 한 곳으로 | (옮길 곳이 셋이라 "다른 상태로 옮기기") | 확정 취소 |

- 생성됨에서 옮길 곳이 둘 이상이면 지금처럼 "다른 상태로 옮기기" 상자, 하나면 [… 취소] 버튼(확인창: "취소하고 '<그 단계 이름>'(으)로 돌아갈까요? 출근표는 그대로 남습니다"). 생성됨이 아닌 상태의 옮기기는 늘 상자.
- [근무표 설정]의 단계 칸 밑에 "버튼 이름은 단계 이름에서 나옵니다(예: '취합 중' → [취합 열기])"를 적는다.

|---|---|
| ~~board~~ | 지운다(FK SET_NULL) |
| boards | JSONField 목록, 기본 `[]`. 고른 근무표의 code 목록(내 근무표 먼저, 나머지 id 순으로 저장). `[]` = 내 근무표만 |

- code 는 만든 뒤 바뀌지 않고 근무표는 지우지 않으므로 FK 대신 code 를 둔다. 읽을 때 없는 code 는 버린다.
- 고른 목록이 `[내 근무표]` 하나면 `[]` 로 저장한다(지금 `remember_board` 가 내 근무표를 고르면 비우는 것과 같다).

### 5.6 GroupKeeper

- 모델·관리 화면 인라인을 지우고 `DeleteModel` 마이그레이션을 둔다. 행은 권한 지정일 뿐 기록(변경·상태)이 걸려 있지 않아 남길 까닭이 없다(원칙 2 "쓰지 않게 된 기능은 지운다"). 그룹 관리자가 하던 멤버 넣고 빼기는 [근무표 설정]의 관리자·입력 담당자 칸이 대신한다.
- 운영 서버에 행이 있으면 업그레이드 전에 목록을 적어 둔다(10.3 확인 명령). 그룹 관리자였지만 근무표 관리자가 아닌 사람이 계속 멤버를 고쳐야 하면, 업그레이드 뒤 근무표 관리자가 그 사람을 관리자로 넣을지 정한다(자동으로 넣지 않는다: 관리자는 회차·배포까지 할 수 있어 권한이 넓어진다).

## 7. [근무표 설정] 화면

### 7.1 들어가기

- 주소 `/settings/?board=<code>`. 메뉴 [근무표 설정]은 어느 근무표든 관리자에게 보인다(`perms.is_admin`). 관리하는 근무표가 둘 이상이면 맨 위에 근무표 고르기(select + [열기]), 하나면 그 근무표.
- 그 근무표 관리자가 아니면 404(`_period` 와 같은 방식). 슈퍼유저라도 관리 그룹에 없으면 못 들어온다(지금 원칙 그대로).

### 7.2 칸(위에서 아래로, 자주 쓰는 순)

화면 하나에 칸(`<section>`)을 쌓고 칸마다 따로 저장한다(한 칸의 오류가 다른 칸의 입력을 날리지 않게). 칸 제목 옆에 한 줄 설명. 모바일(390px)에서는 표가 카드처럼 한 사람씩 세로로 접힌다.

1. **사람**: 표(이름, 아이디, 부서, 구분(관제 있는 근무표만), 계정(발급 전 / 발급됨), 동작). 동작: [계정 발급] 또는 [비밀번호 초기화](확인창: "비밀번호를 새로 만들고 이 사람의 모든 로그인·캘린더·텔레그램·푸시 연결을 끊습니다"), [퇴사](확인창: "로그인할 수 없고 근무표 후보에서 빠집니다. 지난 근무·기록은 남습니다"). 퇴사자는 표 아래 접힌 목록에 [다시 재직]과 함께. 아래 "사람 추가" 폼(이름·아이디·부서(부서가 하나면 숨김)·구분(관제 있는 근무표만)). 아이디 칸은 다음 빈 번호(`<code><nn>`, `add_board` 와 같은 꼴)를 미리 넣어 두고 고칠 수 있다.
   - 임시 비밀번호는 저장 뒤 화면 맨 위 경고 상자에 **한 번만**: "임시 비밀번호 — 이 화면에서만 보입니다. 사람마다 1:1로만 전달하세요. ○○(ops07): xxxx"(관리 화면 액션과 같은 글). 메시지는 지금처럼 Django messages(세션)로 한 번 보이고 사라진다. 로그·이력에는 남기지 않는다.
2. **관리자**: 지금 관리자 목록([빼기]) + 넣기(재직자 select, 이름(부서)) . 마지막 한 명은 [빼기] 대신 "마지막 관리자" 글.
3. **부서 입력 담당자**: 부서마다 담당자 목록([빼기]) + 넣기(그 근무표 재직자). 위에 "담당자가 없으면 근무표 관리자만 입력합니다" 한 줄. 부서가 하나뿐인 근무표도 같은 모양.
4. **회차 단계**: 체크 "작성 중 단계 사용"·"마감 단계 사용", 다섯 이름 칸(끈 단계 칸은 흐리게, 그래도 고칠 수 있다), 미리보기 한 줄("작성 중 → 취합 중 → …", 고칠 때 바로 바뀌는 건 서버가 다시 그릴 때로 충분: JS 없음), 버튼 이름 규칙 설명.
5. **근무 정의**: 관리 화면 인라인과 같은 줄(키(중립 이름, 저장한 줄은 잠김)·이름·시작·끝·자격 근무조·자격 구분·기본 알림·사용) + 빈 추가 줄 하나. 지우기 칸 없음. 위에 관리 화면과 같은 경고(이름·시각을 바꾸면 발송 창이 열린 알림이 한 번 다시 나가고 옛 CSV 열 이름이 맞지 않는다, 저장한 줄은 '사용'을 끈다).

### 7.3 검사(관리 화면 규칙 재사용)

- 근무 정의: `BoardShiftForm`·`BoardShiftFormSet` 그대로(시각, 이름, 켜진 근무조 하나 이상, 시작 시각 서로 다름, 관제 자격, 부서마다 켜진 입력 근무조 하나 이상, 키 잠금, 지우기 없음).

- 단계: 이름 비지 않음·줄바꿈 금지·서로 다름.
- 오류는 칸 옆에 한국어로(`form.labeled`, placeholder 대신 label).

## 10. 마이그레이션과 업그레이드

### 10.1 전제: 운영 DB 는 02c79c5 상태

운영 서버에는 다음이 있을 수 있다고 보고 설계한다.

- 근무표: IT(`collect`) + 시장운영실 등(`direct`, `add_board` 또는 관리 화면으로 만듦).
- 회차: 모든 상태. direct 회차는 보통 취합 중(입력 중)·생성됨(확정)·배포됨, 드물게 작성 중·마감(옛 갈래가 남긴 것, 화면은 "입력 중으로만 옮기기").
- 부서: IT 부서는 입력 그룹 있음, direct 부서는 입력 그룹 없음(`input_group_id` NULL).
- 관리 그룹·입력 그룹 멤버십, `GroupKeeper` 행(1단계 마이그레이션이 그때의 슈퍼유저를 모든 그룹에 넣었다), `RosterPref.board` 값.

업그레이드한 날 지켜야 할 것: IT 회차 흐름·문구·버튼·알림 글자(`tests/test_alarm_texts_it.py` 의 hash 포함) 그대로, 시장운영실 흐름(입력 중 → 확정 → 배포됨, 작성 중·마감 없음, [확정 취소], 채우기 버튼, 빈 평일 경고)도 그대로, 모든 멤버십 그대로, 기억한 근무표 그대로.

### 10.2 마이그레이션 파일(단계마다 하나)

**0023_board_steps(1단계)** — 한 파일에 순서대로:

1. `AddField` Board `use_draft`·`use_close`(기본 참), `step_*` 다섯(기본 IT 이름) + 제약 `board_step_names_set`.
2. `RunPython(forward, refuse_reverse)`(앱 코드 import 없이 `apps.get_model`):
   - `input_mode="direct"` 근무표: `use_draft=False, use_close=False, step_collecting="입력 중", step_generated="확정"`(나머지 이름은 기본값 = 지금 `step_label` 이 끈 상태에 보이던 이름). `collect` 는 기본값 그대로.
   - 입력 그룹이 없는 부서마다 그룹 "<부서 이름> 출근표 입력"을 만들어 붙인다(멤버 없음 = 지금처럼 관리자만 입력). **같은 이름 그룹이 이미 있으면 그 부서 이름을 알려 주며 멈춘다**(0010 과 같은 방식, 10.3 확인 명령으로 미리 본다).
3. `RemoveConstraint board_input_mode_valid`, `RemoveField Board.input_mode`.

`refuse_reverse`: 근무표가 하나라도 있으면 거부("되돌리기는 업그레이드 전 백업 복원으로만" — 2단계부터의 규칙). 끈 단계 조합·새로 만든 입력 그룹을 `input_mode` 로 정확히 되돌릴 수 없다. 테스트·빈 DB 는 지나간다.

**0024_drop_groupkeeper(3단계)** — `RunPython(noop, refuse_reverse)`(거꾸로 돌 때 근무표가 있으면 거부) + `DeleteModel GroupKeeper`. 행은 사라지므로 업그레이드 전에 목록을 적어 둔다(10.3).

**0025_rosterpref_boards(5단계)** — `AddField RosterPref.boards`(기본 `[]`) → `RunPython`: `board` 가 있는 행은 `boards=[board.code]` → `RemoveField RosterPref.board`. `refuse_reverse`: `boards` 에 둘 이상 든 행이 있으면 거부(하나짜리는 되돌려도 같은 값이라 거꾸로 돌 때 `board` 로 옮긴다).

2·4·6단계는 마이그레이션이 없다.

### 10.3 업그레이드 전 확인(읽기 전용, 운영자가 실행)

OPERATIONS "업그레이드·롤백"에 단계별로 적는다(기존 형식: `sudo -u duty sqlite3 -readonly data/db.sqlite3 "…"`, 없으면 아무것도 안 나온다).

- 1단계: 입력 그룹이 없는 부서 중 같은 이름의 그룹이 이미 있는 부서(있으면 `migrate` 가 멈춘다. 업그레이드 전에 관리 화면 "그룹"에서 그 그룹 이름을 바꾼다).
  `SELECT d.code FROM duty_department d WHERE d.input_group_id IS NULL AND EXISTS (SELECT 1 FROM auth_group g WHERE g.name = d.name || ' 출근표 입력');`
- 1단계 참고: 근무표별 입력 방식과 상태별 회차 수(업그레이드 뒤 같은 단계 이름으로 보이는지 대조용).
  `SELECT b.code, b.input_mode, p.status, COUNT(*) FROM duty_board b LEFT JOIN duty_period p ON p.board_id = b.id GROUP BY 1, 2, 3;`
- 3단계: 그룹 관리자 목록(사라진다. 근무표 관리자가 아닌 사람이 있으면 업그레이드 뒤 그 근무표 관리자가 관리자로 넣을지 정한다).
  `SELECT g.name, u.username, EXISTS (SELECT 1 FROM duty_user_groups ug WHERE ug.user_id = u.id AND ug.group_id IN (SELECT admin_group_id FROM duty_board)) AS is_admin FROM duty_groupkeeper k JOIN auth_group g ON g.id = k.group_id JOIN duty_user u ON u.id = k.user_id ORDER BY 1, 2;`

(표·칸 이름은 구현 때 실제 DB 이름으로 맞추고 테스트 DB 에서 돌려 본다. 결과에 실명이 나오지 않게 아이디·코드만 고른다.)

### 10.4 단계별 업그레이드 메모(OPERATIONS 에 옮길 글)

- **1단계**: `migrate` 가 0023 을 적용한다. 보이는 변화 없음. 관리 화면 "근무표"의 "입력 방식"이 "작성 중 단계 사용·마감 단계 사용·단계 이름"으로 바뀐다. 시장운영실 부서에 빈 "… 출근표 입력" 그룹이 생긴다(관리 화면 "그룹"에 보인다). 되돌리기는 백업 복원으로만.
- **2단계(마이그레이션 없음)**: IT 에 보이는 변화가 있다 — 마감 회차에 빈 부서가 있어도 [장중관제 생성]이 막히지 않고 경고만, 입력 근무조가 3개인 부서의 입력 표에 채우기 버튼, 회차 화면에 부서별 [표 입력], 기간을 줄일 때 확인창, 글 도움말 하나로. 업그레이드 공지에 적는다.
- **3단계**: `migrate` 가 0024 를 적용한다. 메뉴 [그룹]이 사라지고 [근무표 설정]이 생긴다. 업그레이드 전에 10.3 그룹 관리자 목록을 적어 둔다.
- **4단계(마이그레이션 없음)**: [근무표 설정]에 사람 칸이 생긴다.
- **5단계**: `migrate` 가 0025 를 적용한다. 기억한 근무표가 그대로 보인다(목록 하나짜리). 근무표 고르기가 드롭다운으로 바뀐다.
- **6단계(마이그레이션 없음)**: 통계 근무표 고르기, 회차 목록 근무표 열.

## 15. 사용자에게 물을 것

1. **부서 출근조·점심 시각도 [근무표 설정]에 넣을까?** 근무 정의에 근무조를 새로 더하면 부서 "가능한 출근조"에도 넣어야 입력 표에 칸이 생기는데, 이 설계에서는 부서 편집이 슈퍼유저(관리 화면)에 남는다. 넣으면 부서마다 체크박스와 점심 시각 두 칸이 늘어난다(구현은 작다). 기본안: 넣지 않음(드문 일).
2. **근무표 관리자가 같은 근무표의 다른 관리자 비밀번호도 초기화할 수 있어도 될까?** 기본안: 된다(같은 근무표 안의 신뢰, 6.2). 막으면 관리자끼리는 슈퍼유저를 거친다.
3. **마지막 관리자 빼기를 막는 것(지금 그룹 화면은 경고만)으로 바꿔도 될까?** 기본안: 막는다(8절).

## 16. 자체 점검

- 1단계 "보이는 변화 없음"과 3절 "빈 평일 경고만·채우기 모든 근무표"가 부딪히지 않게, 사용자 결정은 2단계로 켜고 1단계는 임시 기준 하나(`legacy_admin_entry = not use_close`)로 지금 결과를 낸다(6.1). 그 기준은 2단계에서 지운다.
- 관제 생성에서 빼는 날은 "부서 하나라도 빈 날"이 아니라 "출근 행이 하나도 없는 날"이다. 부서 하나뿐인 시장운영실에서는 지금과 같고, IT 에서 일부 부서만 빈 날을 통째로 빼면 관제 칸이 이유 없이 비기 때문이다(6.1).
- "내 근무표 구역만 편집"을 서버 규칙(`can_edit`: 내 근무표 + 관리하는 근무표)과 맞췄다. 다른 근무표 관리자는 그 구역도 고친다(지금과 같다).
- 생성 가능 상태를 "마감을 쓰면 마감에서만"으로 엄격히 두어, 옛 갈래가 남긴 시장운영실의 마감 회차가 지금처럼 [확정] 없이 "입력 중으로 옮기기"만 보인다.
